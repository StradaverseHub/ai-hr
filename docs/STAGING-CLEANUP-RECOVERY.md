# Completed staging installation cleanup recovery

Policy: `aihr-owned-cleanup-recovery/v1`. This is a separate owner-operated cleanup capability for an already activated, healthy installation whose original immutable cleanup authority and complete audit records were written while its original grant was valid. It does not renew an installation grant or change the normal installer policy. No installation, build, migration, service restart, application source replacement, worker activation or production operation is permitted by this capability.

Use only after concrete source review and a fresh complete CI witness for the frozen recovery source. Keep the original application's CI, build UUID, source, failed operator attempt, original authority and audit bytes at their actual origins. A successful recovery does not retroactively make that failed operator attempt successful.

The operator issuer `scripts/improve/issue-cleanup-recovery.mjs` reconstructs both the original application gate and the recovery-source gate through the existing unchanged pinned `release-ci.mjs` verifiers. These authenticate the repository, workflow, first-attempt complete successful run, independently reconstructed full inventory and required reports, authenticated artifact hashes, and canonical build/source binding. Both runs must remain within their original 24-hour lifetime. After full reconstruction it revalidates both API witnesses, binds the actual helper Git blob and emits a distinct cleanup-only capability valid for at most 30 minutes, bounded by both CI lifetimes. Caller-written PASS summaries are not an issuer input.

The issuer input is a private JSON file with exactly: `applicationPath`, `grantPath`, `helperControllerPath`, `helperPath`, `helperRunId`, `originalControllerPath`, `outputPath`. The application checkout and its original controller remain clean at their original exact SHAs. The helper gate runs from unchanged current main/alpha application controller with the recovery branch as its exact candidate, and with the actual installed application as migration baseline. The recovery branch must leave `.github/ci` unchanged. The issuer writes private evidence only; it does not SSH to staging.

Copy only the exact gated helper and its unchanged `.github/ci` dependencies to an owned private staging directory outside `/opt/ai-hr`. Verify each transferred regular-file hash against the exact Git blobs before execution; reject links, unexpected members, shared permissions or changed bytes. Use the pinned service Node and existing private staging environment without exporting or printing credentials. Retain authenticated issuer output and original records privately. The helper CLI accepts bounded JSON on stdin with an `authorization` field, not arbitrary source or database selectors.

1. `prepare` verifies the original grant and activation/authority chronology, retained audit digests, active compiled byte inventory, original System Testing identity, private environment fingerprint, pinned runtime, service identity, health and complete ordered migration ledger. It durably records a private single-use nonce and full observation, without deletion.
2. Immediately perform the original application's canonical zero-output checksum rsync dry run. Keep its genuine completion time and actual empty output. Source proof has exactly `kind: ACTUAL_CANONICAL_RSYNC_ZERO_CHECKSUM`, the original `source`, empty `output`, and actual `checkedAt`.
3. `commit` selects the exact nonce and prepared-record SHA256. Both the full runtime observation and real source checksum must still be within 60 seconds immediately before deletion. It checks actual runtime/service/env/inode/boot/build and stable complete ledger semantics again, checking ledger observation time separately. It publishes an exclusive intent with file and directory fsync before calling the unchanged descriptor-relative native cleanup. Only the original `next` and `packet` children may disappear; the active build and audit evidence must remain.
4. Full runtime and ordered-ledger observation runs again after cleanup. Keep the separate recovery receipt; perform a fresh final canonical source checksum, preservation checks, release-learning record and outside-source mirror. Only then complete board/deployment handback. Human staging acceptance and production publication/deployment remain separate later decisions.

If any proof changes, expires, lacks authentication, or cannot be durably written, refuse deletion. Keep the original bytes/evidence and diagnose. A consumed nonce is never replayed; a fresh prepare is required after inspecting any failed/partial attempt. A recovery result with `releaseHandbackVerified:false` is deliberately not a completed release handback. Do not forge observation times, weaken the 60-second bound, replace the original grant, or invoke native cleanup directly to bypass these checks.
