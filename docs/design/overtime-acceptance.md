## Explicit resume after actual browser changes

After an owned stop, the parent can add --resume alongside the same bounded attempt, for example --attempt=b2 --resume. Resume is accepted only by the coordinator and its held worker; the fixture rejects it. This is a restart of the preserved journey, never a setup retry.

Resume requires the original fixture-manifest.json and browser-manifest.json, their exact matching preparation facts and original clean-twice candidate, an owned browser-stopped.json and dead prior browser.pid process group, a free fixed port, and the same root, database, namespace, port and current KL date. It verifies the actual restricted application role and a distinct configured migration reader with full tenant visibility (SUPERUSER or BYPASSRLS), plus all exact declared fictional tenant identities. A filtered absence is not accepted as proof of the tenant set. A clean new candidate is required; db/migrations, db/schema.ts and packs/catalog.ts must be unchanged versus both the preparation and last stopped candidates. Missing receipts, a date rollover, schema drift, an active process, unknown tenant or role mismatch refuses. No target is reset or repaired.

The resume branch runs no database creation, migration, seed or fixture. Original preparation manifests and fixture logs stay unchanged. A separate browser-resume-CANDIDATE-TIMESTAMP.json records the preparation candidate, resumed-from candidate, previous stopped receipt, current candidate and fixtureRunsThisCandidate: 0; it grants no new clean-twice or app-acceptance claim. Its separate dev log preserves earlier browser-dev.log evidence. A subsequent owned stop records that resume receipt, and any further resume must validate it as well. Failed runs publish a current-candidate stopped receipt only after all owned groups and DB handles close, with outcome failed, exit code 1 and explicit cleanup provenance; this is never an acceptance PASS. Every separate resume record must be accounted for by the recursively validated prior-stop chain (bounded to 64 records). A newer or orphaned record, mismatched PID, missing current stop or arbitrary resumed-from candidate refuses another resume instead of falling back to an older receipt. The same watchdog, owned process-group cleanup and both-slot/DB lock lifetime apply. Stop through browser.stop in the selected attempt scratchpad; no automatic resume occurs.

Nine complete but unactivated Drafts prepare hourly, fractional flat, salary-based pricing, incomplete-source, false-eligibility, foreign-company and foreign-tenant journeys. Its top-level await and import.meta.url keep module execution and worktree-root resolution consistent without changing the package-wide module format. ## Coverage and limits that remain explicit

- Setup declares no current-as-past grade/team/profile values. Additional approved selection axes need their actual canonical choice and historical/prospective facts; empty options are not success. Exercise all supported axes via UI or scoped owner regressions before completion.
- A true sourceUnavailable/unreadable calculation is not forged with SQL. The committed metadata/RLS regressions own those fault controls; an actual naturally refused input is the browser case.
- Currency 0/3 precision, cross-midnight placement, session policy, overlapping deductions, salary cap, controlled retroactive/version closure, raw retarget denial and concurrent lock behavior require their focused pure/DB controls as well as representative UI. The fixture does not manufacture all those states.
- Payroll mapping, currency/precision, cycle, country minimum, approval and policy failures remain real failures. Missing statutory data or other preflight prerequisites must be recorded and fixed through their canonical UI/owners, never bypassed to obtain a green screenshot.
- The local notification module is absent for the fictional tenants, notifications seed flag is off and IDENTITY_EMAIL_SOCKET points to a nonexistent local path. No identity/SMTP/mail worker is started. Email is outside this acceptance run and no delivery claim is permitted.
- This runner proves preparation/cleanup only when actually run. It cannot certify browser behavior, complete financial correctness, production-role migrations, full regression gate or deployed behavior.
