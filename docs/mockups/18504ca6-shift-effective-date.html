Save
Press Save and the old shift is gone. There is no date to say when the new one starts and no line saying what the old one was, so the system can no longer answer “which shift was this person on last month?”.

What does not happen: nothing already recorded is recalculated. Every day’s worked hours, lateness and overtime were frozen the moment that day was calculated. What does happen, and you would not expect it: past days start showing the new shift beside figures that were never measured against it, and any old day later corrected or re-imported is re-measured against today’s shift — because today’s shift is the only one on file.

4One limit you should see before you approve, and what this picture leaves out

Dating a change before one already recorded is refused for now

10/08/2026
This employee already has a shift change dated 15/08/2026. A change dated before that one cannot be added yet.

Past dates and future dates are both fine — as long as they come after the last change already recorded for that person. Slotting one in earlier is a rarer case and deserves its own request. Saving twice for the same date simply replaces that entry; periods can never overlap.

Deliberately not in this picture

  • No re-processing screen. You asked for “Recompute Attendance” separately and it should be built once, so this request stands it down. Dating the shift is what makes a recompute give the right answer — approving both, in that order, gets you the whole thing without it being built twice.
  • No hours, no overtime figures. Nothing already calculated is recalculated by this change, so there is no new number to show you.
  • Editing a shift itself — changing MB28’s hours, breaks or overtime windows — still affects every date that uses it, past included. That hole stays open and is worth its own request.
  • The Roster screen already does part of this today, dated day by day, and a roster entry for a date always beats the shift on the profile. It is not drawn here because it is not what this request builds.
