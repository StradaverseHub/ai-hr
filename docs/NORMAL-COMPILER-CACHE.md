# Normal whole-project compiler graph cache

The normal `alpha-staging-ci` typecheck job is wired to an authenticated graph cache in the isolated performance branch. Actual runtime validation is pending at this checkpoint. Every admitted invocation runs the complete current strict TypeScript project. No compiler PASS, application test, migration, build or deployment is replaced.

## Identity and trust

The actual candidate, controller and run remain separate. Cache state comes only from a completed successful first-attempt compiler job in an authenticated same-repository manual run or alpha push. PR jobs can consume eligible graphs but do not publish graphs for later candidates. Actual artifact ID/repository/run/ZIP digest/size, private fixed JSON members, original compiler zero exit/raw diagnostics/file count, owned-resource cleanup, exact state bytes/version/age and provenance must validate.

The reader also fetches the original authenticated controller Git tree and requires every actual critical compiler, extraction, configuration-policy, toolchain-setup and workflow blob to match its current trusted implementation. Reported hashes alone cannot establish that match. A single immutable bootstrap tuple is separately pinned to the independently verified original diagnostic source067301b35/run40243921832/artifact12617977681/ZIP digeste631a892…; it expires normally and is never relabelled as a newer compilation.

Actual Node/TypeScript/Next/Linux/x64, compiler implementation bytes/flags/heap/path, root configuration, dependency locks, generated Next types and mobile inputs must match. A distinct source needs an authenticated bounded ancestor comparison; the compiler discovers/checks all current files afterward. Identical source still runs the compiler. Extended/referenced configurations retain cold compilation; they do not produce eligible reusable graphs under this policy. No matching graph, stale state, failed job, wrong code, unavailable API or invalid bytes produces an accepted cache hit. Lookup has a20second budget, then the actual compiler runs cold.

## Execution and resource controls

The first attempt uses the validated compiler-only capacity profile, pinned Node22.23.3, all existing web/tooling/mobile dependencies and real Next type generation. It uses a shallow source checkout because required compiler inputs are at the frozen HEAD and cache ancestry is authenticated through GitHub. Four explicit database URLs target closed port1. It keeps the8GiB heap and bounded4GiB owned swap; at least12GiB is needed before dependencies and8GiB before reserving swap. Remaining source disk is checked before/after compilation with a2GiB floor. Linux `prlimit` caps each regular compiler output file at64MiB; noEmit preserves the full existing project scope.

Cache hits and misses both invoke the real installed whole compiler. Actual command exits, diagnostics, positive complete file count, raw log/state digest, source/controller restoration and owned cache/swap cleanup are recorded. A failed compiler prints its actual bounded output to the job log and cannot publish new state. Legacy rerun attempts retain the prior whole-compiler command and resource admission; this optimization does not change the release policy's first-attempt evidence requirement.

A successful current command publishes a new immutable `whole-compiler-state-v1` packet only after verified wrapper cleanup and only for an admitted publisher. It contains exactly `compiler-log.json`, `envelope.json`, `producer.json`, `state.json` and `swap-cleanup.json`. Retention is one day; it is optimization data, not a receipt. CI policy `aihr-staging-ci/v3` explicitly authenticates this one optional artifact alongside all unchanged mandatory artifacts. Missing test artifacts cannot be replaced by it. Failed-only source assessment authenticates its namespace/provenance and still requires fresh compiler/build prerequisites; no test-unit coverage is obtained from cache data. Unknown/foreign/duplicate/unsafe artifacts remain refused.

## Exact-path validation before adoption

The default-off `managed_compiler_probe` diagnostic executes this actual normal helper on one standard Ubuntu runner. It has no application suite, database, production build or deployment. Its optional `managed_compiler_force_invalid` control first authenticates the pinned real graph, corrupts only a private snapshot copy, requires the digest refusal to actually occur, then exercises mandatory cold compilation and fresh publication. It cannot silently call a missing-graph situation a tested corruption refusal. A later fresh-VM run must authenticate the newly published managed graph through the controller-code tree and still run the whole compiler.
