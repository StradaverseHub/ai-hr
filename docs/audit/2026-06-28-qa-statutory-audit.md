## Synthesis

# ai-hr QA + Malaysian Statutory Audit Report

## Verdict

**Not production-fit as-is. There are two hard blockers in the payroll kernel that must be fixed before any payroll run touches real employees.** The loan negative-net guard is blind to CP38/TP1/zakat/unpaid-leave, so a payslip can be persisted with a **negative net pay** (verified: basic 3000 + CP38 2500 + loan 1400 → net **−1272.80**), and that figure propagates into the bank payment-summary export — i.e. the system asserts the employee owes the company money for the month. Compounding it, loans **auto-settle to a zero balance once the instalment count reaches `durationMonths` regardless of the real outstanding balance**, silently writing off un-recovered employer principal with no distinct audit event. Beyond payroll there is one genuine **cross-company data-disclosure (RLS) defect** — an HOD can see another company's employees/payslips via a cross-company department parent link — and a financial-ledger RLS gap letting a loan subject self-write their own loan rows. The leave engine has two high-severity correctness defects (permanently-unapprovable emergency-leave child requests on fractional AL balances; a probation/contract review sweep that re-opens a fresh review every cron run forever). None of these are isolated to exotic inputs — they fire on ordinary low-salary-with-garnishment, fractional-AL, and multi-company-tenant states. **Statutory exposure is real**: negative/incorrect net pay and silently-mutated CP38/loan figures feed the bank file and would corrupt the figures underlying EA forms and statutory remittances, so these are compliance blockers, not just bugs.

## MEDIUM / LOW (grouped by area)

### Loans / payroll kernel
- **MEDIUM — `estimateNetBeforeLoan` ignores all period params, uses a coarse 50%-of-gross floor** (`core/loans.ts:482-514`). Accepts `companyId/periodStart/periodEnd` then `void`-discards them; the 50% figure isn't derived from statutory tables, EPF/PCB election, or citizenship/age, and omits CP38/TP1/zakat/unpaid. The accepted-then-discarded params hide an unfinished implementation. *Fix:* compute a real estimate or document it as a coarse upper bound **and** pair with the hard generate-time clamp from C1 so correctness doesn't depend on the estimate. (Root-cause sibling of C1.)
- **MEDIUM — Test asserts the clamp *implementation* (`loanDeduction < 5000`) not the *requirement* (`net ≥ 0`)** (`test/loans-payroll.test.ts:109-123`). The negative-net guard test uses a loan with no other post-tax deductions, giving false confidence the guard is sound. *Fix:* add a test combining a loan with a large CP38/unpaid/manual deduction on a low salary asserting `netPay >= 0` — currently a correct red test (net = −1272.80).
- **LOW — `updateIndividualTxn`/`deleteIndividualTxn` throw `BatchNotDraftError` on a missing row** (`core/payroll-individual-txn.ts:203,246`). A not-found surfaces a misleading "batch not draft" error to UI/callers. *Fix:* throw a distinct `TxnNotFoundError`, reserving `BatchNotDraftError` for the real non-draft case.

### CP38
- **LOW — CP38 supersede leaves a closed row whose month-aligned `validTo` still matches the boundary month (latent overlap)** (`core/cp38.ts:90-104` + `273-303`). The window predicate uses inclusive `validTo >= periodMonthStart`, contradicting the gist EXCLUDE constraint's exclusive `[)` daterange. Masked today by deterministic first-per-employment dedup (June correctly resolves to the new value), but a future summing caller (e.g. a report) would double-count the boundary month. *Fix:* make the predicate treat `validTo` as exclusive (`gt` not `gte`) to align with the constraint; add a test asserting a single CP38 row matches the boundary month in the raw query.

### Replacement-Leave / TOIL
- **MEDIUM — `closeReplacementLeaveYear` reads `company.leaveCycle` with no WHERE filter** (`core/toil.ts:662-663`). Selects an arbitrary company row and applies its calendar-vs-anniversary cycle to **every** accrual across **all** companies in the tenant. In a mixed-cycle multi-company tenant, the non-selected company's employees get swept at the wrong boundary → wrong forfeit/convert dates and amounts. *Fix:* join `company` in the active-accrual SELECT and branch the boundary per employee (or run the close per company). Add a mixed-cycle multi-company test.
- **MEDIUM — REPLACEMENT consumption gated on `TOIL_ENABLED` at approval time, decoupling the ledger debit from the register** (`core/leave.ts:799-806`). The ledger debit posts unconditionally but `consumeReplacementLeaveTx` only runs when `TOIL_ENABLED==='true'`. Approve with the flag off → accrual rows stay `active`; re-enable → `runToilExpiry`/`closeReplacementLeaveYear` post a **second** debit for already-spent days, driving balance negative and raising spurious ORP-owed events. Operationally unusual trigger (stable feature gate), but real financial-integrity impact. *Fix:* decrement the register whenever the consumed type is REPLACEMENT regardless of the flag, or block REPLACEMENT approval while TOIL is disabled.
- **LOW — TOIL convert-to-pay uses floating-point dollar math instead of integer cents** (`core/toil.ts:554,571-575`). `round2(days * (wages/26))` with per-row rounding can drift on aggregation. Currently advisory only (event carries a "reconcile at pay time" note, no disbursement), and it actually *matches* the sibling advisory ORP code at `payroll.ts:1689` rather than violating a universal convention — so the framing is weaker than a true convention breach. *Fix (optional):* value ORP in integer cents and round once at end of summation if a future payroll integration ever consumes `amountOwed` directly.

### Hiring ↔ review wiring
- **MEDIUM — Hire `provisionalEndOn` is never written to the review end-date columns, so auto-review never fires for new hires** (`core/org.ts:144-149`). `hireEmployee` writes only `employment.provisionalEndOn`, but the review workflow reads exclusively from `probation_end_date`/`contract_end_date`/`internship_end_date` (sole writer: `setReviewEndDate`). A full-time hire's 3-month provisional end (or a contract/intern explicit end date) opens **no** review and shows no due date — HR must redundantly re-enter it. *Fix:* on hire, also write the provisional end into the matching review column by employment type, or have `computeReviewWindow` fall back to `provisionalEndOn` when the type-specific column is null. Add a hire→sweep-sees-due-date test.

### RLS / financial ledger
- **MEDIUM — `employee_loan` / `loan_repayment` RLS `WITH CHECK` uses `can_see_employment`, letting the loan subject self-write their own loan ledger** (`db/migrations/0120_loan_management.sql:71-77`). `can_see_employment` grants the employee SELF access to their own employment, so the policy provides **no DB backstop for admin-only loan writes** — an employee could INSERT/UPDATE/DELETE their own loan/repayment rows under RLS. *(Finding truncated in source; substance confirmed.)* *Fix:* tighten the `WITH CHECK` on these financial-ledger tables to an admin/authorized-writer predicate rather than `can_see_employment`, keeping subject SELECT but not write.

## Malaysian compliance subsection (statutory-return / audit risk)

These findings carry direct LHDN/EA-form and bank-remittance exposure and should be treated as **release-gating** for any live payroll run:

- **Negative / corrupted net pay reaching the bank file (C1).** A persisted negative `netPay` flows into the bank payment-summary export. Beyond the operational absurdity, the wage and deduction figures behind statutory wage records and the EA form become unreliable when the kernel can produce sub-zero net. **No net pay < 0 may ever be persistable or exportable.**
- **CP38 garnishment integrity (C1, CP38 low finding).** CP38 is a court/LHDN-ordered post-tax garnishment. The loan reserve is blind to it (C1), and the supersede convention has a latent boundary-month overlap. CP38 amounts must be deducted exactly as ordered and must never be silently reduced, double-counted, or pushed against a loan reserve that ignores them — these figures are auditable against the LHDN garnishment instruction.
- **Silent loan write-offs with no distinct audit event (C2/H1/H3).** Employer-funded advances forgiven on instalment-count alone, recorded with a generic `loan.settled` event indistinguishable from a real payoff, leave the loan ledger misstating money owed — an audit-trail and financial-records integrity gap.
- **TOIL convert-to-pay / ORP valuation (TOIL medium + low).** Replacement-leave double-debits and ORP amounts computed on the `wages/26` (EA-1955) basis are advisory today, but if/when wired to disbursement they directly affect payment-in-lieu owed to employees; the second-debit path (`TOIL_ENABLED` decoupling) can raise ORP-owed events for already-spent days.
- **Statutory-deduction precedence (C1, `estimateNetBeforeLoan` medium).** The reserve heuristic conflates statutory load with a flat 50% and never consults the actual EPF/SOCSO/EIS/PCB tables or the employee's EPF/PCB election, citizenship and age. While the authoritative payslip math uses real calculators, the guard built on top of it is unsafe; the fix must make the **generate-time clamp** authoritative so statutory deductions always take precedence over loan recovery.

**Recommended gate:** ship nothing to a real payroll cycle until C1 and C2 (and their siblings H1/H3) are fixed and a red-test combining loan + CP38 + unpaid leave on a low salary turns green, plus H2 (cross-company RLS) is closed.

### CRITICAL

#### 1. Loan negative-net guard ignores CP38/TP1/zakat/unpaid — payslip net pay goes negative
- **Area:** loans / payroll kernel · **Reviewer:** `qa:payroll-txn`
- **File:** `core/loans.ts:482-515 (estimateNetBeforeLoan) + core/payroll.ts:1477-1481 (generatePayslips)`
- **Detail:** prefillLoansForBatch clamps the reserved instalment against estimateNetBeforeLoan, which approximates available net as a flat gross*0.5 and explicitly ignores every other post-tax deduction (CP38 garnishment, TP1, zakat, unpaid-leave, manual deductions). generatePayslips then computes totalDeductions = statDeductions + slipUnpaid + slipExtraDeduct(incl. cp38) + slipLoan and net = grossPay - totalDeductions with NO final clamp. I confirmed with an integration probe: basic 3000, CP38 2500, 1-month loan 1400 → gross 3000.00, totalDeductions 4272.80, netPay = -1272.80. The payslip and the bank payment-summary export both carry a negative net, i.e. the system says the employee owes the company money for the month. The whole point of the reserve-time clamp ('never let loans drive net below zero', loans.ts:417-421) is defeated because the clamp is blind to the other deductions that are applied alongside the loan.
- **Recommendation:** Make the negative-net guard authoritative, not a 50%-of-gross heuristic: either (a) compute the real statutory+CP38+TP1+zakat+unpaid load in estimateNetBeforeLoan, or (b) add a final clamp in generatePayslips so slipLoan (and ideally cp38) cannot drive net below 0 — clamp slipLoan = min(loan, max(0, grossPay - statDeductions - slipUnpaid - slipExtraDeduct)) and carry the unrecovered remainder forward on the loan schedule rather than applying it. A net pay < 0 must never be persistable.
- **Verified (high confidence):** Confirmed independently by reading the code. (1) estimateNetBeforeLoan (core/loans.ts:482-515) returns gross*0.5 as available net headroom and explicitly ignores all post-tax deductions — the docstring (lines 477-480) and inline comment (507-508) admit it is a coarse "conservative 50% of gross" heuristic covering only statutory worst-case, never CP38/TP1/zakat/unpaid/manual deductions. (2) The reserve-time clamp (loans.ts:419-421) clamps takeCents only against this availableNet, so with basic 3000 the headroom is 1500 and a 1400 instalment passes through unreduced because the clamp never sees the 2500 CP38. (3) generatePayslips (core/payroll.ts:1474-1481) folds CP38 into slipExtraDeduct = round2(en.deduct + cp38), then totalDeductions = statDeductions + slipUnpaid + slipExtraDeduct + slipLoan and net = round2(grossPay - totalDeductions) with NO final clamp — grep for Math.max(0,...net)/net<0/clamp on net in payroll.ts returned nothing (exit 1). The persisted payslip netPay (line 1499) and the payment-summary/bank export therefore carry the raw negative figure. The probe arithmetic is consistent: gross 3000, CP38 2500 + loan 1400 + ~372.80 statutory = 4272.80 totalDeductions → net -1272.80. (4) Test coverage gap is real: test/loans-payroll.test.ts:109 exercises negative-net only for a loan-only case (salary 1500, loan 5000, no other post-tax deductions); no test combines a loan with CP38/TP1/zakat. The reserve-time clamp's stated invariant ('never let loans drive net below zero') is genuinely defeated because the clamp input is blind to the other post-tax deductions applied alongside the loan in the kernel. Severity critical is justified: a negative net pay is persistable and propagates to the payslip and bank payment export. Recommendation (b) — a final authoritative clamp in generatePayslips with carry-forward of the unrecovered loan remainder — is the correct fix; the 50%-of-gross heuristic in estimateNetBeforeLoan cannot be made authoritative without duplicating the full kernel.

#### 2. Clamped loan instalments + duration-reached auto-settle silently writes off the outstanding balance
- **Area:** loans apply ledger · **Reviewer:** `qa:payroll-txn`
- **File:** `core/loans.ts:538-549 (applyLoansForBatch)`
- **Detail:** fullyRepaid = newOutstandingCents <= 0 || newInstalmentsPaid >= loan.durationMonths. The second disjunct force-sets outstandingBalance to '0.00' and status='settled' whenever instalmentsPaid reaches durationMonths — regardless of whether the balance is actually paid off. Because the reserve clamp (finding above) can reduce each instalment's dueAmount well below the scheduled amount, a loan can hit durationMonths with a large real balance still outstanding, and the kernel then forgives it. Confirmed with a probe: basic 1000, advance principal 1800 over 2 months (900/mo instalment, but only ~500/mo headroom) → after 2 cycles the loan is status='settled', outstanding 0.00, instalmentsPaid 2, while far less than 1800 was actually deducted. This is an uncontrolled employer financial loss with no event/flag indicating a write-off occurred.
- **Recommendation:** Decouple auto-settle from the instalment count: settle only when newOutstandingCents <= 0. If instalmentsPaid >= durationMonths but outstanding > 0 (because instalments were clamped/partial), keep the loan active (or move to a 'in_arrears' status) and append a distinct event so the shortfall is visible and recoverable — never zero a non-zero balance.
- **Verified (high confidence):** Confirmed independently at core/loans.ts:538-549. fullyRepaid = newOutstandingCents <= 0 || newInstalmentsPaid >= loan.durationMonths; the second disjunct force-sets outstandingBalance:'0.00' and status:'settled' based purely on instalment count.

The dependent clamp is real and wired through: prefillLoansForBatch clamps each reserved instalment to estimateNetBeforeLoan headroom (50% of gross, line 509) via takeCents = Math.max(0, Math.min(dueCents, availableCents)) (line 420) and PERSISTS the clamped value into loanRepayment.dueAmount (line 425). applyLoansForBatch then reads appliedCents = toCents(Number(rep.dueAmount)) (line 533) — i.e. the clamped amount, not the scheduled amount. So instalmentsPaid increments once per cycle regardless of how little was actually deducted.

Reviewer's probe arithmetic verified: basic 1000 → 500/cycle headroom (1000*0.5); advance principal 1800 over 2 months → computeLoan yields schedule [900,900]. Cycle 1: take=min(900,500)=500 → outstanding 1300, paid 1 (1<2, active). Cycle 2: take=min(900,500)=500 → outstanding would be 800, paid 2 → 2>=durationMonths(2) makes fullyRepaid true → outstanding forced to 0.00, status settled. Only 1000 of 1800 recovered; 800 silently written off.

Tests do NOT cover this: every auto-settle test (test/loans-lifecycle.test.ts:144-160, 187-192) and test/loans-payroll.test.ts only use scenarios where either the clamp never bites (principal within 50% headroom) OR they assert loanDeduction but never the post-settle outstanding-vs-actually-paid invariant. Test (c) (loans-payroll.test.ts:109-123) proves the clamp exists but uses durationMonths:1 and asserts only net>=0 and loanDeduction<5000 — it never checks the loan's final outstanding/settled state, so the write-off goes unverified.

No distinct write-off event: the settle path emits 'loan.settled' (line 565-572), identical to a legitimate payoff and to manual settleLoan — the forgiveness is invisible to audit. The recommendation (settle only when newOutstandingCents <= 0; route count-reached-with-balance to an arrears state + distinct event) is correct.

Severity nuance: requires the clamp to bite (instalment > ~50% of gross), realistic for short-duration advances on lower salaries but not the modal loan. Given it is a silent, unflagged, unrecoverable write-off of real employer funds with no event signalling it, critical stands.


### HIGH

#### 3. Leave working-day counter hardcodes Sat/Sun as the rest day, ignoring the configurable roster the attendance engine uses
- **Area:** Leave — working-day counting · **Reviewer:** `my:employment-law`
- **File:** `/Users/zenlam/Projects/ai-hr/core/leave.ts`
- **Statutory ref:** Employment Act 1955 s.59 (rest day — one per week, employer-designated, not fixed to Sun); s.60E (annual leave counted in the employee's working days)
- **Detail:** workingDays() (lines 242-250) and the EL working-day filter (lines 551-554) treat dow===0 (Sun) and dow===6 (Sat) as non-working for every employee. But core/attendance.ts (lines 178-180) resolves rest days from the roster / attendance_policy.workingDays — so a 6-day-week worker (rest day Sunday only), a Friday-rest-day Kelantan/Terengganu employee, or any non-Mon-Fri schedule has a DIFFERENT rest-day pattern than what leave assumes. Consequences: (1) for working_days-counted annual leave, a Saturday worker who takes a week off is debited only 5 days when 6 working days were actually consumed (employee over-credited; employer under-charges the balance) — and vice versa for a Friday-rest employee whose leave spanning a Friday is wrongly debited. (2) Kelantan/Terengganu/Johor/Kedah weekend is Fri-Sat, not Sat-Sun, so the leave engine mis-counts annual-leave consumption for an entire region. This mis-states leave balances that feed the EA form and any leave-encashment-on-termination figure.
- **Recommendation:** Resolve the employee's rest days from the same roster/attendance_policy.workingDays source the attendance engine uses (isoWeekday) rather than hardcoding 0/6. At minimum make the Fri-Sat vs Sat-Sun weekend state/company-configurable, since the four northern states' default weekend differs.
- **Verified (high confidence):** CONFIRMED. The two engines genuinely disagree on rest days.

ATTENDANCE (configurable): core/attendance.ts stores rest days as data. attendancePolicy.workingDays is an ISO-weekday array (DEFAULTS.workingDays = [1,2,3,4,5], line 44), and per-employee rosters carry an explicit rosterAssignment.isRestDay. scheduleFor() resolves day type via `pol.workingDays.includes(isoWeekday(date)) ? 'workday' : 'rest_day'` (line 180), and the bulk path does the same (line 555). So a 6-day-week, Friday-rest, or any non-Mon-Fri schedule is honored.

LEAVE (hardcoded): core/leave.ts workingDays() (lines 244-247) excludes days where `dow === 0 || dow === 6` using getUTCDay() — Sat/Sun, fixed. The EL/Emergency-Leave cascade filter repeats the identical hardcode (lines 551-553), and a third call at line 580 (annualEnd split) uses the same workingDays() helper. leave.ts has NO reference to policyFor, attendancePolicy, or isoWeekday anywhere (grep clean) — it structurally cannot see the configured roster.

LOAD-BEARING: workingDays() is not dead code. It drives working_days-counted leave types (line 412, gated on lt.counting === 'working_days') and the annual/unpaid Emergency cascade split (lines 539, 580). The file's own comments (lines 252-254 'count a working-days span the same way attendance will' and 536-537 'honouring the employee's holidays/state') assert parity with attendance that the code does not deliver — for the weekend pattern specifically. (Holidays ARE shared via holidayDatesFor; the weekend/rest-day axis is the gap.)

CONSEQUENCE: For a Saturday-working employee, a week off is debited 5 days when 6 working days were consumed (employee over-credited, balance under-charged); for a Friday-rest employee, leave spanning a Friday is wrongly debited. These balances feed the EA form and leave-encashment-on-termination, so the mis-count propagates to statutory output and final-pay figures.

STATUTORY: EA 1955 s.59 designates one rest day per week chosen by the employer (not statutorily fixed to Sunday); s.60E counts annual leave in working days. The four northern states (Kelantan, Terengganu, Kedah, Johor) observe a Friday-Saturday weekend by default, not Sat-Sun. Both legal claims check out.

SEVERITY CALIBRATION: Kept at high, not critical. The default policy is Mon-Fri and default leave behavior coincides with it, so only companies/employees that configured a non-Mon-Fri roster are affected. But that population is real and material in MY (the four northern states by default, plus the very common 6-day operations/retail week), and the error is silent and touches statutory leave balances + termination pay.
