# 0128 — Versioned System Testing and personal execution records

Status: accepted implementation direction; verification and release pending.

Board: 9689f5d3. This extends the existing System Testing owner. It does not grant access to any tested business function.

A test case keeps its existing tenant identity and visible TC number. A published instruction version is immutable. Administrators edit a separate draft with a revision check, then publish it. A version records its instruction content, hash, publisher and provenance. The migration may record the definition present at upgrade as an explicitly labelled baseline. Earlier runs have unknown instruction version; assigning them to that baseline would invent history.

An assignment belongs to a real tenant login and a case. It identifies the current target instruction version. An execution belongs to that assignment, tester and version. Each save appends an observed status/result/comments record and advances a revision-checked execution pointer. A newer publication makes existing assignments require retest; it never changes an earlier pass or makes it a pass of the new instructions. Administrators may read team progress and manage assignments but cannot save an execution as another tester. A tester filter is a read filter, never write authority.

The System Testing entitlement is checked by its canonical service first. Database policies separately enforce the actual tenant, assignment, tester and administrator boundaries. Neither assignment nor publication changes Personnel, Payroll, Attendance or other business grants. Missing business authority is an explicit blocked/not-applicable result, not an opportunity to impersonate an administrator. Module removal retains stored history but prevents access through this module's service until restored.

The reviewed catalogue uses stable semantic case and function identifiers. Its guides contain prerequisites, fictional test data, ordered actions with an expected result for each action, overall expectations, business authority and applicable country/configuration constraints. Screen/pack inventory identifies coverage gaps; no gap is automatically called covered. A title match is only a suggestion for explicit one-to-one legacy mapping, never permission to overwrite a case. Catalogue absence cannot archive a case.

Updates compare the exact current library snapshot with the reviewed catalogue. Confirmation re-derives that preview under a tenant library lock, checks its exact hash and selected semantic identifiers, and records a stable update identity in the same transaction as publication. Repeated confirmation is idempotent. Local changes conflict visibly rather than being overwritten. Each guide carries a reviewed fingerprint of its exact source subset. A changed source without that reviewed fingerprint update requires review; a reviewed source change creates a new version/retest even when guide wording is unchanged. automated source comparison is not an author of business instructions.

Build identity uses the five explicit compile-time Next `env` substitutions for nonsecret source ref, build-record UUID, catalogue hash and source-content hash, plus a bounded serialized source-path/hash record. No web request shells out to Git or trusts a mutable runtime BUILD_ID/environment/file as authority. Missing, malformed or mismatched compiled identity produces review-required. Official release/config wiring is implemented below; actual compiled-artifact and Linux verification remain required. A successful official build is not proof of arrival, service parity or any manual test pass: its observation keeps `activeServiceVerified:false` and `manualExecutionVerified:false`.

## Official release and compiled provenance boundary

After the authentic exact-commit gate receipt and complete local type check, the common official release
path prepares one clean-HEAD record with a fresh build-record UUID. Its source subset comes from the
committed reviewed catalogue; installed bytes and clean HEAD are checked again before shipping. No
per-guide reviewed fingerprint is rewritten. The record is published once in private caller-owned
`~/.aihr-gate-state/system-testing-builds/<UUID>/system-testing.json`, outside the source rsync.

After rsync, a narrow trusted CLI receives the canonical bounded JSON over SSH stdin. Only the expected
source ref and UUID are command arguments. It validates the exact tuple, catalogue digest, required
source-path set and each installed file digest without Git, rejects symlink/escaped/unbounded sources,
and publishes once under private `~/.aihr-system-testing-builds/<UUID>/system-testing.json`. Writable or
symlink storage ancestry is refused, including the ordinary `/var/tmp` deploy-state location. There is
no mutable latest record, public record endpoint, arbitrary caller-selected web path or URL ingestion.
The serialized compile source record is capped at64KiB and the whole transfer at80KiB, with refusal
rather than truncation; these bounds still require actual Linux launch verification.

The detached deploy receives `--testing-build-record=UUID`; the argument and announcing source ref are
captured before private production environment loading. After the existing dependency install and
audit preflight, the build CLI reloads that exact private record, rechecks installed bytes and launches
the existing canonical production build with all five exact metadata overrides. The deployment's
build-before-migrate order, type-error refusal, state/follower, restart, gate learning and board binding
remain separate owners. A nonofficial deployment supplies empty values for all five fields, even if
stale values exist in `.env.production`; unsetting alone would let Next load them again.

Only a child build that actually exits0, writes a fresh valid `.next/BUILD_ID`, leaves the preparation
unchanged and still matches installed reviewed source may append the private immutable
`successful-build.json`. It binds the tuple, prepared-record SHA256, actual Next build ID, timestamps
and platform. A build-record UUID is not the Next build ID. Failed/partial builds get no successful
observation, and neither this observation nor existing release-learning evidence proves active service
arrival or a human execution pass. An independently authorized rendered catalogue preview can compare
its compiled sourceRef/buildRecordId/catalogueHash/contentHash with the build publication. Actual
artifact behavior under absent/poisoned runtime values remains an explicit verification outcome.

Execution screenshots use their own execution-scoped bounded storage and download authorization, not a borrowed Feedback ownership relationship. Defect and improvement creation use the existing Feedback writer in the same explicit transaction as the execution link. A retry returns the same link. A board item being fixed may request retest, never mark a human execution passed.

Migration0561_versioned_system_testing, index561 and timestamp1791900000041 are centrally allocated after the first release's0559/1791900000039 watermark. The earlier unapplied0557 proposal is renumbered by the parent; no historical applied migration is rewritten. The parent owns the actual journal union and migration execution.

Verification still required: restricted app-role assignment/execution/attachment boundaries; two independent testers; concurrent stale saves and publish; legacy baseline honesty; exact-hash update retry/concurrency/conflict; atomic Feedback retry; module removal; eight-area catalogue coverage; six-locale/mobile/keyboard/theme journeys; official built identity and independent arrival evidence. ## Canonical Feedback reporter extension and consumer audit

Source review found that valid assigned tester logins can have no Person or Employment. The original Feedback graph required an employment, and `myEmployment` also excluded future-terminated employments although canonical `app.login_blocked` still permits that login. Assignment eligibility must not be narrowed to conceal this gap. System Testing therefore raises canonical Feedback as its actual login, with NULL employment context. It never selects an arbitrary employment, borrows another reporter or creates an employee. Existing employed submissions retain their recorded employment scope and history.

The canonical `submitFeedback` writer now accepts optional/null employment context only with the actual live `ctx.userId`, revalidated against the tenant login, archive state and canonical login lifecycle. `reporterUserId` is never an input. The exact existing validation/write/event path accepts an explicit caller Tx for atomic idempotent execution linking. Personal Feedback read/review/attachments/revisions/block answers follow that login. A cross-user user-only report is visible only to an existing explicitly group-wide administrator; a company-scoped admin does not gain tenant-wide access through missing company context. No additional product or business grant is created.

Audit map:

- `feedback_request`: employment becomes nullable; a real reporter login is required when absent. Its creation binds to the current live principal; converting a stored reporter into another identity is refused. Existing employed rows are not backfilled or re-owned. Withdraw remains a status transition; user-only rows gain no ordinary DELETE policy.
- `feedback_attachment`: employment context mirrors its actual parent and may be NULL. The original employed read scope is retained. User-only evidence is append-only under its parent owner/group-wide visibility, with the actual uploader. Existing canonical 10 MiB validation remains unchanged. Operator plan mockups continue to derive parent employment rather than assume a nonnull value.
- `feedback_plan_revision` and `feedback_block`: every read, append and close/resolve policy follows the canonical Feedback parent. Existing immutable plan/question triggers remain. No tenant-only close policy may bypass a private user-only parent.
- `domain_event`: existing scoped-admin audit reading could otherwise expose a user-only report title or reason.
