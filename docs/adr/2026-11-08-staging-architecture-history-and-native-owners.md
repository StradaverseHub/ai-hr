# Preserve installed history and native owners when integrating architecture changes

Status: source integration in progress; staging qualification and deployment pending. Production remains held and its current compatibility is unverified.

The architecture must preserve current behavior as well as improve read latency. A checkout's branch name, successful superuser-owned fixture or correct SQL file hash does not establish installation compatibility. The release candidate must retain the actual installed feature lineage, ordered migration history and native ownership/RLS profile.

The stock engine applies only journal timestamps above the installed watermark; moving an old draft into a new checkout does not execute it. A generic missing-hash replay would also lose the strict installed-order contract.

Integrate the feature histories through a normal merge. Preserve the exact707-entry prefix and all original SQL bytes. The target-specific, still-uninstalled architecture suffix receives centrally coordinated timestamps/indices above known reservations, in its original dependency order. The explicit reservation manifest records every old/new identity. Original source commits, failures and successful component receipts remain immutable. This is a closed staging lineage; it does not assert that the old drafts were absent from every installation or that production tooling already admits the new history.

Renaming a superuser, disabling RLS, granting broad application rights or changing live ownership to satisfy a fixture is not an installation solution.

For the source union, retain cached company context plus independently copied selected IDs and allowed-company IDs; shared workflow immutable assignments and administration over every assigned company; live command decision checks and batched task projections; and recorded payroll totals alongside bounded inquiry paging. Presentation changes must not recompute financial truth or widen scope. Six locale catalogues retain both feature sets.

Qualification must distinguish three proofs. Component tests establish exact guarded function changes and application behavior under real restricted roles. A populated installed-prefix rehearsal must separately reconstruct the reviewed706/707 history, including the two audited original historical SQL versions, and apply the final suffix with the normal engine under the native restricted owner. A fresh-chain test establishes a third claim. None can substitute for another.

The populated rehearsal must preserve ordered ledger rows, internal IDs, immutable histories, recorded money and effective grants; demonstrate every new migration executed exactly once; prove a second engine invocation changes nothing; reject unknown predecessor/source/owner/history before mutation; and exercise early/middle/late failure and actual interruption/restart/restore behavior. Native function and relation owners, default grants, special-purpose owners and forced RLS must match the declared profile. Disposable fixture ownership changes must be bounded to their own database and explicitly restored; never use REASSIGN OWNED against the shared postgres role.

Future build gates must include restricted-owner execution and a rendered, nonempty authorized/denied journey for each changed module or submenu. Read models retain fresh identity/scope/date/permission adjudication and the canonical query/money owners. They must demonstrate complete counts/facets/selected identities with bounded returned rows, without clipping a server-owned authorized population or introducing per-row policy/index probes unnecessarily. Worker counts are qualified against actual CPU, memory, connection and workload budgets; an eight-worker run on a four-CPU host remains an oversubscription diagnostic.

Before staging, the final combined source still needs the required whole compiler/build/migration and browser gates, module-wide latency checks, and bounded2/4/8-worker evidence with zero page Busy, crashes or unexpected blocking-lock failures. Existing exact baseline and arrival verifiers remain enforced. A shared staging lease and current restorable private backup precede installation. Production compatibility requires its own actual source/build/ordered ledger and role-profile inspection before any future mutation; staging qualification grants no production authority.
