# Database work admission before connection checkout

Status: candidate; hosted behavior, compatibility and mixed browser/load qualification pending. Production deployment is held.

## Preserved business contract

Admission controls when a transaction starts. It does not change its principal, tenant, grants, isolation, locks, SQL, calculation, audit or commit boundary. A queued operation has not been accepted as a business outcome. A cancelled queued read never starts a transaction. Once admitted, cancellation does not falsely declare a committed command rolled back. Callers must retain existing durable receipts and uncertain-outcome handling.

`db/client.ts` shares one admission owner per physical postgres-js pool, including hot reload and multiple `createDb` handles. All `withTenant` calls enter it before checkout. `withPoolWork` admits existing raw transaction owners without introducing a transaction or changing their SQL. Session entitlement reads, internal authentication transactions and the import worker's entitlement refresh use that same gate. Explicit transaction leaves remain connection-free. Other direct raw queries and owner maintenance connections still need separate accounting; this change does not claim to govern them all.

The authentication hot-path inventory additionally routes pool-owned encrypted-record reads, credential/principal checks, web/mobile principal lookups, dev login-block checks and cold idle-policy reads through this same physical gate. Explicit transaction record/credential leaves keep their function identities and do not acquire nested admission. The refused-login audit retains its original single SQL effect, with admission before starting and no retry. Queued read cancellation propagates as an infrastructure/cancellation outcome, never an absent or newly valid identity. Session, MFA, password expiry, family revocation and existing request memoization semantics remain owned by their original services.

The serial session/credential/family/principal/password-policy read phase uses one admitted reserved connection, without BEGIN or a new transaction snapshot. Each original SQL statement remains a fresh statement. This avoids multiplying admission waits between serial checks. The connection is always released before account-expiry observation or idle-session writes enter their original independent transactions. This scope performs no external IO and creates no identity/result cache.

Cold idle-policy admission and cancellation failures propagate without manufacturing or caching a policy. Failed shared loads remove only their own in-flight entry, allowing a later request to read the configured limit. The existing ADR-0171 fallback for an actual admitted SQL-policy read failure remains unchanged.

An admitted read composition owns every child until settlement, including later IO after a sibling fails. Inbox, nested Performance/Rewards providers and parallel Home readers use `settleReadGroup` over independent read thunks. It drains every child, preserves ordered successful results and rethrows the first observed original failure. Synchronous throws and already-started shared child promises follow the same rule. This prevents early logical admission release, early transaction completion and detached query fan-out. It does not retry reads, suppress owner failures, run commands or change owner authorization. Controlled native-IO tests exercise the actual inbox and providers through second-phase assessment/decision queries.

The active ceiling equals the existing physical pool size. Background transactions use at most one quarter of it (minimum one); interactive transactions may use all idle capacity. Bank import phases, clocking import writes and report-spec execution explicitly inherit the background classification. The gate changes neither job authorization nor report disclosure. The shell also classifies its passive streamed approval preview as background. Active Home cards, explicit task views, and decision commands retain interactive admission. Direct exports and other existing workers still require an inventory before claiming complete workload classification.

The pending ceiling is 2,048 divided among declared application workers, with a 30-second admission deadline. Pending reads remove themselves promptly on their existing AbortSignal. Work already in a transaction is never evicted by this admission timer. Interactive work is preferred, with a background turn after three interactive admissions when its lane has space. Within a lane, the tenant with least active work is preferred; equal counts retain FIFO order. Queue telemetry must not expose tenant identifiers or HR payloads.

While interactive work is queued, admission additionally accounts for occupied pool time. Background time costs three units and interactive time repays one, preserving the intended quarter share across small worker pools without preempting an executing unit. Both lanes are accounted continuously at scheduling boundaries, so completion order cannot lose interactive credit. With no interactive queue the debt resets and background work can use spare capacity. This corrects the two-connection rounding case, where the minimum one background slot otherwise permits half of each worker's pool to remain occupied indefinitely. It is a contended-time scheduling share, not an instantaneous cross-process semaphore or a bound on an individual owner transaction. The same active/pending/time limits and tenant ordering remain in force.

The 7 November diagnostic42341431180 recorded594 queue-full log markers across four workers, with no queue-timeout markers or heap failure. These markers are not unique request counts. One reviewed amplification path was the passive shell summary opening multiple background child reads for each page before admission. The physical gate now caps background pending work at one quarter of its unchanged total pending ceiling. A separate logical passive-read gate admits `withBackgroundReadWork` before fan-out, with active capacity equal to the pool's background ceiling, at most2,048 logical waiters across declared workers, and the same30-second deadline. Logical waiters hold no connection. Same-tenant nested composition shares that logical admission, all children retain their physical admission and authority, and the parent awaits them. This adds a separately bounded operation queue while reducing child fan-out. Hosted500-operation/interactive-reserve tests and complete browser/load verification remain required. This is not a permission-result cache or a retry policy.

`AIHR_APP_WORKERS` and `AIHR_DB_TOTAL_CONNECTIONS` must be supplied together. Startup rejects a per-process pool multiplied across workers that exceeds the declared total. Existing single-process installations retain their pool default. The declaration is an operator-controlled process count, not automatic discovery or an assertion about every connection on a server. Web plus dedicated workers, maintenance and operator reserve must fit the database's measured connection/memory budget. A one-connection process cannot reserve a second connection for interactive work.

Bank import capacity deferral leaves durable job/row checkpoints intact for its normal next tick. It must not turn an unstarted row into a permanent data failure. The next phase reads checkpoints again; no blind replay of external effects is introduced.

Only `BankImportRowRejectedError`, raised by the canonical row analyzer for a deterministic changed-data rejection, is counted as a failed row. SQL, connection and unexpected errors stop the job with committed checkpoints intact and a bounded message. Recovery remains a new validated upload through the existing public flow. No automatic retry of an uncertain command or external effect is introduced.

## Qualification and remaining gates

Focused tests must prove physical connection reserve, queued cancellation, overload recovery, tenant fairness, rollback release and no context leakage. Existing Attendance, Bank import, reports, permissions and audit tests must pass. A caller holding a transaction must pass that transaction to nested owners; independent nested background transactions can exhaust a small lane, so call graphs and representative owner compositions are part of qualification.

The former unbounded per-tenant Attendance queues are replaced by one bounded process admission owner: at most half the application pool in active writes, two per tenant/interactive operation and one import across the process. PostgreSQL command locks remain unchanged. Raw connection users remain explicit follow-up review items. Final acceptance additionally requires aggregate worker budget checks, mixed-workload outcomes and the browser preflight. Do not describe this candidate as a complete system overload guarantee merely because the semaphore tests pass.

## Phase 3 addendum (10 November 2026): complete and fair admission

Admission now covers every raw `client` query in `app/`, `lib/`, `core/` and `packs/` (`withPoolWork`, `withSystemWork`, or the `admittedAuthSql` facade); `test/raw-client-admission.test.ts` keeps new raw calls out. Because permits equal connections, nothing waits in postgres.js's own queue, so every query has the 30-second admission deadline.

Three lanes share one gate. `authentication` (login, session, recovery, invitations, health) is served first, has `ceil(P/8)` permits tenant work can never hold (none when P < 3), and is capped at `ceil(P/2)`. Interactive and background keep their existing ordering. A tenant's fair share is `max(1, floor(5P/8))` permits and it is work-conserving: a tenant alone on the pool can use every permit except the login reserve, and once another tenant has work running or waiting the over-share tenant gets no new permit until it is back under its share, with the other tenant served first. Held permits are never revoked, so an arriving tenant waits for the next permit to free; the phase 1 and 2 removal of long transactions is what keeps that wait short. One tenant may hold at most three quarters of the pending queue. `db/capacity.ts` carries the formula and its derivation from pool size and worker count. Nested work inside a tenant's own transaction is exempt from the cap so it cannot deadlock against itself.

Every process counts against PostgreSQL's limit: `web + background (AIHR_DB_BACKGROUND_CONNECTIONS) + reserved (AIHR_DB_RESERVED_CONNECTIONS) <= max_connections - superuser_reserved_connections - reserved_connections`. Non-web processes declare `AIHR_DB_PROCESS_ROLE=worker` and a pool of two in their units. `deploy/deploy.sh` refuses a mismatch before anything restarts; the web process logs the same check at start.

Capacity failures (`DatabaseAdmissionError`, `57014`) retry automatically only where the work is a read: `readOnlySnapshot` transactions, reads marked `idempotent`, and routes declared read-only. Writes are not retried. A failed page reaches `app/error.tsx` or `app/global-error.tsx`, a translated state that re-fetches by itself when capacity was the cause; APIs answer 503 with `Retry-After`. The limit remains a last-resort guard, not an expected path.

## Stall budget addendum (11 November 2026): a draining queue is served, not refused

The v17 gate (run 42958137526) refused 2 of 100 concurrent Home role reads for one tenant with `queue-timeout`. The default web pool of 10 gives a lone tenant 8 permits (2 are the login reserve); its per-tenant queue limit is 1,536, which the burst never approached. Under runner load each read held its permit for about 2.4 s or more, so the burst needed longer than the fixed 30-second deadline to drain, and the last waiters were refused while the queue was still moving. A large employer's 9 am Home load is that shape, and a refusal there is the Busy outcome the owner forbids.

The 30 seconds are now a stall budget, not a deadline. A waiter is refused only when its own queue (its lane and tenant, which is admitted in FIFO order) has admitted nobody for the whole budget, checked in quarter steps, so a stalled waiter still leaves between one and 1.25 budgets after its queue last moved and exactly at the budget when its queue never moved. A draining burst is served however long the drain takes. An absolute ceiling of four budgets (120 s at the defaults, `maxWaitMs`) remains for every waiter, far above every proxy and client timeout, so it only sheds queued work nobody is still waiting for under sustained overload. Fairness is unchanged: another tenant's request still takes the next freed permit, logins keep their reserve, and background work keeps its quarter share and its debt accounting.

A refusal is raised before any work starts, so `db/client.ts` asks for the permit again (`retryAdmissionRefusal`, the read retry's three attempts and 75-second budget) for pages, commands such as clock-in, and login, whether they read or write. Two cases keep a single wait: background work, which keeps its deferral so an import yields and resumes from its checkpoints, and code that already holds a permit (inside a tenant transaction, raw pool work or a shared read carrier), so a held connection is never kept through a retry. Statement cancellations (57014) and pooler refusals still retry only for declared reads, because they can follow work that already ran.

`test/performance/home-burst-admission.test.ts` measures a 100-read same-tenant burst held for 2 to 4 seconds per read, about 37 s to drain, with another tenant's single reads, same-tenant clock-ins and Personnel search, and login-lane reads and writes running during it. Every request must be served.
