# Remembered-device MFA for embedded login

Status: implementation candidate; staging qualification and binding review pending.
Owner direction: LOGIN chat, 2 November 2026. Reduce repeated authenticator prompts while retaining verification for first/new-device login, password recovery and a configurable interval. This feature is separate from the frozen Editorial login redesign and does not change the coordinated release order.

## Decision

Use explicit per-device remembering after successful TOTP verification. A correct password alone cannot register trust. The owner-confirmed tenant default is30days, administrator-configurable from0to90days;0requires MFA at every fresh login. This is a fixed duration from the actual factor verification, not a sliding expiry. The period is expressed in days (30days approximates a month), not calendar months. The owner confirmed30days and both web/mobile in the LOGIN question replies.

New/unremembered browsers, private browsing, app reinstalls and expired or invalid proofs require the normal enrolled factor. TOTP enrollment and password recovery retain their existing requirements. Recovery codes can still complete the existing supported flow, but never issue a remembered-device proof. Forced password changes also do not mint a proof; the next normal MFA can remember the device. Existing web8hour sessions, native15minute access/8hour refresh families and tenant idle sign-out limits are unchanged. Remembering a factor never keeps a user signed in.

The server still checks the current password, exact credential/organization, principal eligibility and password-expiry policy. Opaque256bit random proofs use digest-only record keys and encrypted authenticated storage. Proofs bind subject, tenant, credential version, browser/native carrier, policy revision, verified time and absolute expiry. Password reset changes the credential version, invalidating all old device proofs. Account eligibility and grants remain authoritative on every login/session. Any tenant MFA-policy revision invalidates prior proofs, even when disabling and re-enabling or saving the same interval. A shared/exclusive transaction lock serializes proof validation/issuance with policy changes. There is no client-declared MFA success or provider-permission change.

The browser transport accepts proofs only in a separate `__Host-aihr_mfa` Secure/HttpOnly/SameSite=Strict/path=/ cookie, with no Domain. Browser JSON never receives that proof. Successful password reset also clears that browser's cookie; other devices' ciphertext becomes invalid through credential-version binding. Native transport ignores all browser cookies, accepts only its own proof in bounded JSON, and returns a proof only after complete verification. Native replies validate proof shape and bounds before persistence.

The native app uses device-only SecureStore, keyed to approved identity namespace, canonical organization and username. A sandbox marker clears surviving iOS Keychain trust after reinstall. Writes and stale-generation cleanup are serialized so a cancelled previous login cannot overwrite the next user's proof. Optional secure-storage failure falls back to MFA; it does not turn into bypass or prevent otherwise completed verification. Proofs persist through ordinary logout by design; the next login still requires the password. Users must not select remembering on a shared device.

## Authority, audit and storage

The existing group-administrator Login settings surface owns this tenant policy, alongside password/session settings. Both application and fresh database principal/group-admin checks are required; tenant derives from the authenticated context, never form input. Optimistic revision refuses stale saves. Policy writes and their audit event commit together. Authentication audits record use/registration of a remembered factor without raw proofs or credentials. UI vocabulary is separately scoped in all six supported languages; existing shared message catalogs are unchanged.

The existing encrypted auth record owner stores policy/proofs; no schema or applied migration changes are needed. New cryptographic/governance permissions are not added. The canonical provider transform fingerprint changes because reviewed auth implementation bytes changed; existing literal AI approvals are not silently transferred. Both source manifests and exact approval impacts must be assessed separately before release. Member behavior checks cannot authorize deployment of another source or aggregate.

## Required evidence

Hosted real-storage tests cover password-before-proof, default/opt-in, fixed expiry/no sliding renewal, tenant/subject and browser/native separation, credential-version/reset invalidation, forced-password MFA, recovery-code refusal to remember, policy revision/disable/re-enable, stale updates and non-admin denial. HTTP tests prove carrier isolation, no raw browser token in JSON, strict cookie flags and reset clearing. Native storage tests cover namespace/account separation, expiry, reinstall and cancelled writes. Rendered web/native controls cover opt-in and submitted values; policy and vocabulary checks cover all six languages. Whole root/native typechecks and canonical production build remain separate claims. Exact final-source full gate, current-baseline staging/ledger/arrival and rendered login acceptance remain required under the coordinated release policy.
