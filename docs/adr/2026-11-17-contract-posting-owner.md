# Contract postings use the Personnel and Movement owners

The approved Contract journey creates a pending Personnel posting after its causative letter is released. The workflow supplies only a case, frozen run and step reference. The native owner derives the decision revision, dates, next contract number, subject person and posting approver group. Repeating a step or another matching workflow cannot create a second posting for the same decision revision.

The Personnel posting is a proposal. Approval uses the existing Movement dispatcher, information writer and dated assignment writer in the same app-role transaction. Renewal advances the contract period and native contract number. Conversion uses the existing Employment Type Change movement to change the dated employment type to Full-time and clear contract dates; it preserves tenure, organisation dimensions, contract-number history and confirmation/probation facts. Both outcomes append a record-only Contract Termination for the expired old period to the existing Movement history. That record never terminates the employment. No compensation writer is called.

Posting-group membership authorizes this fixed action even when the person has no general Workforce maintenance permission. It does not mint an HR role, a Workforce grant or an owner-role HR transaction. A private intent binds the approved `contract_staff` posting to the current backend, transaction, session login and actual actor. The native service-information hook and RLS admit only the complete frozen OLD/NEW Employment images. Conversion permits only the existing assignment's exact closure and a new version with identical dimensions, Full-time type and agreed effective day. There is no additional Employment trigger and no general writable-row exception.

Future movements use the canonical scheduled Movement ledger. Approval records the pending movement without making future dates/type/counter current early. The ordinary effective-date application rereads the immutable source intent, checks the subject identity and source period and retains the original group. The old-period expiry record is appended on actual application. A stale source fails instead of changing another person's record. Pending native first-post-retirement intake also holds an unapplied posting; completed receipts and historical pay confirmation remain available. The case may be renewed/converted after posting approval, with a separately outstanding manual-pay attestation; the UI must distinguish a scheduled Personnel movement from an applied one.

Manual Payroll entry remains the Payroll owner's existing human action. A posting approver can attest that entry only after an approved posting has a canonical movement receipt. The attestation closes the pay-pending case and records an audit entry; it never reads, compares or changes a Payroll amount. Posting queues and task metadata expose no current or agreed salary, signing policy or full case JSON. The attestation response is limited to case ID, revision, stage and confirmed state.

The source-dispatch wrappers preserve the actual preceding Probation and Offboarding posting owners, including Offboarding rejection and approval behavior. Contract adds only `contractRenewal` and `contractConversion`; End and declined-renewal workflows create no termination posting in this merge. They use the separate native Offboarding handoff, after which People Ops records termination manually in Personnel Management until clearance integration exists.

Verification is performed on standard GitHub-hosted Actions. Local compiler, application tests, builds and development servers are not used. Focused checks establish development claims only; finished UI acceptance and the integrated release gate remain required before review/merge/release approval.
