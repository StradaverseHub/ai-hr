# ADR-0119: Shared Personnel declarations and Employee Master report reads

Date: 2026-10-15. Status: accepted implementation direction under approved board items c44575e0 and 5f9c8062. Verification remains pending until the acceptance map is demonstrated.

Personnel fields have one declaration owner: `lib/personnel-field-registry.ts`. Stable literal IDs survive label changes. Each declaration states the screen label, tab/section, machine owner/field, type/unit, grain, history coverage, sensitivity, reporting capabilities and import writer contract. Forms, import templates and report catalogues consume these declarations. A future stored scalar on an existing owner needs one declaration; it must not need a second report-specific field list. Derived fields and new registers still require an authoritative owner read, never guessed database access.

Reports consume typed owner values through explicit read seams. They do not calculate salary, statutory charges, Leave entitlement or Attendance again. Missing stored history is an unavailable value with a reason, distinct from a blank or zero. A past-date condition against a current-only field refuses visibly. Historical record IDs with current catalogue names disclose that label coverage.

A report subject is an employment or an unactivated draft. Drafts retain their own identity and held Employee ID, and remain outside active headcount and compensation totals. Rehire and concurrent employment do not collapse into one person; person counts are separately distinct.

All-record columns from one register align by the same record identity. Unrelated expanded registers produce independent report sections/sheets. Latest overrides remain explicit per column. Aggregation deduplicates at the field owner's record grain, excludes drafts from active totals, and refuses incompatible currencies/units or unavailable measures. It does not multiply salary by family/document rows or sum borrowed Leave pools independently.

Template ownership and role sharing are enforced by separate database command policies. A private report has no administrator read bypass. A visible administrator can edit/delete a report but cannot discover a private report by ID. Field category grants reuse the existing configurable company/tenant granular permission owner. A generic admin role does not override an explicit category denial; a template never grants record, company, field or pack access.

A report read can explicitly request `withTenant(ctx, fn, {readOnlySnapshot:true})`. Drizzle starts a repeatable-read/read-only transaction before session GUCs or data reads. Every participating owner receives that exact transaction handle explicitly. Default callers retain their transactions; no ambient context, mutable session transaction or nested auto-join is introduced. Manual/scheduled audit writes occur separately after the read.

Optional scheduled delivery uses the existing managed job/mail owners. Durable per-schedule/recipient/occurrence identity prevents duplicate sends. The worker resolves selected user identities, opt-in and fresh report/field/company access, then builds the workbook from that recipient's authorised snapshot. The web tier supplies no arbitrary email address, message body or workbook bytes to the managed sender. Permission/consent revocation and uncertain SMTP acknowledgement are delivery decisions, not retries that can silently widen access.

Consequences: historical gaps remain visible; projections require explicit owner seams; a newly declared field with no implemented read is not treated as working merely because it appears in a catalogue. The acceptance map in `docs/verification/5f9c8062-acceptance.md` records the required journeys, including private admin isolation, salary denial, all-record totals and delivery revocation. No test or deployment result is asserted by this decision.

Report-attachment consent is the new `employee_master_reports` category in the existing notification preference/policy owner. It is off by default and remains outside the workflow-dispatch category tuple. Its verified opt-in binds the exact issuer/subject, user and employment, a hash of the current profile address and a verification instant. A profile address change durably clears this report consent, including change-away/change-back, without changing workflow consent. A stored opt-in never establishes current provider verification; the managed sender must check the live provider account and `emailVerified` again.

Schedules store exact `{userId,employmentId}` pairs, one selected employment per user. A concurrent employment is never selected by matching email or array order. Every human schedule save generates `reviewedRevision`; managed due-date and lease updates preserve it. An occurrence retains logical schedule/report IDs, the recipient pair, owner, report version, reviewed digest, schedule revision and the Notifications owner's typed consent/policy revisions. It retains no address or report rows. These identities and revisions cannot be mutated and survive report/schedule deletion. A queued occurrence is eligible only while the current schedule is enabled with the same reviewed revision/digest, version and pair, and current policy/consent/identity/access still permit it. Re-enabling creates a new reviewed revision, so old queued work does not resume.

`resolveEmployeeMasterRecipients(ctx, identity?)` is the Notifications-owned server read. It supplies real recipient contexts with fresh principal grants and entitlements; the sender's roles or exemptions are never copied to the recipient. UI options receive only pair IDs and a scoped name/Employee ID/company label. The revision contract is `{consentAfterSequence,policyAfterSequence,consentUpdatedAt,policyUpdatedAt,consentVerifiedAt}`. Revision timestamp strings use UTC ISO with six fractional digits (`to_char(... AT TIME ZONE 'UTC','YYYY-MM-DD"T"HH24:MI:SS.US"Z"')`) and must not round through JavaScript Date; the worker copies the original timestamptz values and reads the same precise strings. All five fields are compared exactly at send; timestamps distinguish withdrawal/re-enable even when an event watermark alone would not.

`renderEmployeeMasterDelivery(recipientCtx,{reportId,expectedVersion,scopeIds,recipientEmploymentId,consentRevision,scheduleId,scheduleRevision,reviewedDigest})` authorizes the current schedule and consent before and after workbook generation, and returns server-generated XLSX bytes. It does not perform SMTP or assert delivery success. The managed transport alone owns durable start/lease/outcome and records sent/failed/skipped/uncertain. Lost SMTP acknowledgement or acceptance followed by a lost outcome commit remains uncertain and must not produce an automatic retry. This managed transport and runner integration is still required. Scheduled files use the exact saved as-at date; no rolling date is inferred. Month-only source values and predicates preserve `YYYY-MM`, including text cells in Excel, without inventing a day.

Historical company authorization consumes the canonical company's strict `provenCompanyDatesTx` and `provenCompanySegmentsForPeriodBulkTx` readers. These use nonsuperseded assignment records, preserve NULL/missing/ambiguous gaps and clamp to recorded hire/termination; they never use the payroll compatibility filler as historical proof. Past/ended subjects lacking dated membership are excluded before domain reads. The disclosed unknown-scope count is restricted to already-RLS-visible current members of selected companies for which the caller has report-category access; other companies' unresolved membership contributes no count. Current open facts may use the recorded current employer, with no claim about earlier history. Historical register rows need overlap with a strictly proven selected-company interval; unknown gaps grant no permission. A separate generic notice discloses unavailable history only for currently authorized selected-company members. The existing payroll compatibility resolver is unchanged.

Historical-scope exclusion notices survive export: Excel includes a Report notes sheet, PDF repeats the scope notice, and CSV is packaged with a Report-notes.txt companion when such notices exist. Data CSV files retain their actual column header as the first row. An export cannot silently look complete after its preview disclosed unresolved historical scope.
