# ADR-0139: counted database phase reuse for the Board 1 fixture repair

> Decision record at its recorded date; implementation/status observations are historical. Verify current source and later amendments. [Branch/release policy](../REPOSITORY-AND-ENVIRONMENTS.md) governs operations.

Accepted 2026-10-24. The owner explicitly requested safe reuse after all eight database chunks pass and the local fixture is restored, followed by the test-only Home repair and verified Board 1 release. This is a bounded verification policy enhancement under impact policy version 3.

The original 65ee43f full attempt remains FAIL: its no-database phase had three failures in one synthetic Home session fixture. All eight database phases completed naturally and independently passed. The preservation wrapper compared the complete fixture identity, database OIDs, configuration hashes and logical contents before and after the run. A phase-reuse receipt records these facts separately from newly executed tests; it never becomes a full PASS baseline or resets full-regression history.

The only product repair permitted is the exact fingerprinted, additive change to employee-home-landing.test.ts. It attaches a resolved same-tenant entitlement snapshot, retains all six original cases and assertions, and adds notification-enabled/disabled prop assertions. Application code, dependencies, schema, configuration, test helpers, database tests and installed runtime versions are unchanged. The initial verification bootstrap has an explicit file list; any other delta refuses reuse. This is intentionally a narrow repair contract, not a general test-change exemption.

The gate archives and hashes the original plan, append-only learning record, full inventory and classification, controller, all eight logs, original failure log, wrapper and restoration snapshots. Validation recomputes the committed baseline inventory and exact classification/round-robin partition. Each chunk needs its own exit zero, positive exact file/test counts, a natural footer and an unambiguous complete-controller summary. Partial, skipped, todo, duplicate, missing, timed-out and uncollected coverage refuses.

The final clean candidate runs the complete current no-database suite against a closed port with one worker. After the owner explicitly requested rerunning only the no-database phase, phase-reuse policy version 2 uses a frozen-product no-DB strategy. Every original DB chunk remains evidence for its original commit. The exact byte-delta contract proves the application, migrations, DB tests, shared fixtures and dependencies are unchanged. The old/new graph identifies consumers of the changed verification machinery; those controls execute separately with every DB URL pointing at a closed port. A database connection attempt fails this strategy. There is no new application DB phase, and the receipt must contain zero fresh DB batches. Generic source-reader expansion and mandatory guards already passed in the original DB run; they are not presented as newly executed tests. The fixture preservation wrapper must restore and compare again before finalization can issue PASS. A pending successful phase run still has a FAIL receipt until restoration and full provenance revalidation finish.

Release recomputes clean HEAD, ancestry, environment, current production baseline, the narrow delta contract, every artifact hash, original and new inventories, graph fingerprint, fresh counts and both restoration comparisons. It refuses changed production, stale evidence (seven days or ten released versions), altered original learning, unknown source or incomplete machinery coverage. Production is read again after TypeScript validation. Missing phase-reuse revalidation never falls through to another tier.

Whole-repository type checking, production builds, runtime acceptance, migration rehearsals, deployment, service restart and health/arrival checks remain separate required evidence. The original red attempt is preserved. No application security gate, entitlement rule or financial assertion is weakened.

A narrowly proven exception distinguishes a process RSS monitor from a repository reader: unchanged code may be excluded from source-read expansion only when every imported fs operation is readFile, every reference is a direct call, and every path is a literal /proc path or the numeric PID status of its uniquely bound child_process.spawn result. Escaped aliases, shadowed bindings, other fs APIs, changed monitor code and unknown paths retain broad coverage. This proof is enabled only for phase reuse after the exact product-byte preservation check. Ordinary impact selection keeps its previous conservative behavior.

Owner scope reaffirmed on 2026-10-24: “Can we just re-run the no-db test? Since the failure comes from that part and the 8 db chucks already passed”. This supersedes the earlier conservative plan to refresh unrelated database source readers. The receipt explicitly records strategy frozen-product-nodb, policy version 2, the complete fresh no-DB inventory and any separately executed closed-port verification controls. It never claims a new full-suite PASS. Outside the exact fingerprinted fixture repair and bounded verification bootstrap, reuse is refused.

Owner extended the repair contract on 2026-10-25 (MYT): “Fix CSS, reuse DB results”. Phase-reuse policy 3 permits exactly the fingerprinted Atelier phone header CSS and its paired browser regression. The header wraps scope and account controls onto separate rows below 640px. Both files must match reviewed before/after hashes; an omitted paired file or any other CSS/browser edit refuses reuse. Application logic, schema, DB tests, shared fixtures, dependencies and configuration remain frozen. Fresh browser checks, complete no-DB checks, closed-port tooling controls, build and actual runtime review are required for the final candidate; the original eight DB results remain separately attributed to 65ee43f. Earlier statements that all application bytes are frozen apply to policy 2; this explicit CSS exception supersedes them in policy 3.
