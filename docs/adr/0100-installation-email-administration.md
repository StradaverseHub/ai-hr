# ADR-0100: Installation email administration

Date: 2026-10-11
Status: Accepted

The relay for identity invitations and password recovery is an installation fact. An HR administrator's company scope must not imply control over authentication for other tenants. Keycloak's realm SMTP configuration remains authoritative for sending; the application provides a constrained administration workflow.

A root-enrolled capability binds an exact external issuer/subject to its existing internal user and tenant. It grants no HR role or customer-provisioning operator role. Every page/action checks authenticated identity and every settings operation rechecks enrollment, binding revocation and login status in private database functions. The sidebar exposes Email delivery under Admin only to this capability. The role matrix's scoped-session eligibility has an explicit capability scope note.

The web process receives no `manage-realm` client secret. A dedicated system user runs a root-owned bundled service over a systemd-activated Unix socket, accessible to the app OS account. It has a separate realm service client with `manage-realm` and a database login with explicit grants only for operator lookup and metadata-only audit. Its API accepts only view/save/test/apply/readiness operations, not arbitrary realm paths or JSON. This limits an app compromise's available identity operations; it does not protect against an attacker who controls the trusted web process impersonating an enrolled actor on this socket. The root administrator and installation OS remain trusted.

The service's two database functions live in the private `identity_email` schema. Its login receives no `app` schema usage: the live privilege review found older helpers in that shared schema with inherited PUBLIC EXECUTE. A separate schema prevents this new login from reaching those helpers without changing existing application privileges. Acceptance exercises the installer grants with an actual isolated database role and proves that shared principal/audit helpers and HR tables remain inaccessible.

The service executes a private root-owned copy of Node alongside the bundled agent, with root-owned parent directories that the web account cannot write. The installation's `/opt/node20` runtime belongs to `ubuntu` and cannot be the dedicated service's executable. Both the runtime and bundle require controlled administrator updates. Scheduled identity backup maintenance may use root for its private database dump, but executes application session-pruning code as `ubuntu`.

Passwords are never returned by the UI or written into the HR database/audit. Keycloak's file vault resolves versioned aliases into files readable by the settings service and identity service only. Vault files are protected plaintext, not encrypted storage. Include them in encrypted off-host backups. Old versioned files are retained to support uncertain writes and rollback; prune only after confirming that no active configuration or draft references them. There is no broad secret read endpoint.

Saving creates a new per-actor draft and invalidates its previous test. Testing sends a real Keycloak SMTP test message to the fixed bootstrap-owner address, which is configured on the isolated service account during provisioning. Enrollment must attest that same recipient. It does not accept a recipient from the browser. Activation requires an exact draft ID, an unchanged active configuration revision, a successful test within 30 minutes, explicit receipt confirmation and a durable intent audit. Only `smtpServer` and `resetPasswordAllowed` are updated. A failed test leaves the active relay unchanged; an uncertain write retains its secret and reports uncertainty. Invitations fail closed until the agent recognizes an activated configuration; recovery remains disabled until activation. Existing active recovery can continue if the administration service is down.

The revision covers observable realm configuration and the service's private activation receipt. Keycloak masks SMTP credentials in its Admin API. A trusted root/realm administrator can make out-of-band changes that bypass this workflow, including a password-only change the masked read cannot detect. Such changes require reconciliation through a fresh explicitly supplied password and successful test. The UI is the supported configuration path; private realm administration is an emergency trusted operation, not a concurrent settings writer.

DECISION: Support implicit TLS only (typically port 465) with trusted certificate and hostname verification. Keycloak 26.8.0's default sender sets STARTTLS `enable`, not `required`; accepting STARTTLS here would promise a guarantee the actual identity sender does not enforce. We will not add a weaker fallback or a certificate-bypass switch. A STARTTLS-only relay needs a separately reviewed solution. Both test and production delivery use Keycloak's actual sender and vault rather than testing with a different SMTP library.

The first owner can enroll a password and TOTP directly in Keycloak before app cutover. An owner-only application cutover can precede mail activation so the owner can use this screen; invitations and recovery stay unavailable until the tested relay is active. Do not invite customers until that prerequisite is satisfied. The owner must complete first login/MFA; the installer never impersonates them.
