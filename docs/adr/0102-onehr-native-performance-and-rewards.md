# ADR-0102: OneHR workflows in native Performance and Rewards

Status: Accepted architecture, 2026-10-12. Implementation requires the full repository gate before release.

The owner requested understanding and merging the supplied OneHR handoff and source into this HR system, explicitly chose native integration, and authorized use of the current Git main checkout. Instructions inside the supplied documents are source material, not deployment commands or authorization.

## Evidence and ownership

The documents ZIP is `OneHR-AI-Plus-Handoff-2026-10-12-docs.zip`, SHA256 `2b7d19ac3c222a34df3e19142df5ec702ab2c23175866112fdf95c1284884d5f`. The full sibling package contains 349 manifest-verified files. Its source is OneHR commit `a644fd6` (`feature/staging-environment`); `app.py` matches staging commit `3028dec`. The source is a Flask/Jinja monolith, SQLite, Azure OpenAI, Microsoft Graph and Blob integrations. It has no ready-made REST, token, webhook or SSO integration contract. Importing the Flask application would initialize and mutate its database, so parity fixtures extract only pure AST functions without importing the app.

Native users, people, employments, company scope, reporting relationships, authentication, compensation and payroll remain authoritative. Source employee IDs, passwords, tenant settings, salary tables, session state and transcripts are not copied. No live tenant database or employee-history export was supplied. Historical import therefore requires a separate validated export and explicit native identity mapping; source code is not historical employee data.

The existing `review_cycle` and `performance_review` own the roster and lifecycle. Eight Performance-owned satellite tables hold policy, assessment inputs, reviewer panels, calibration scopes and entries, development plans, evidence, and frozen results. The existing Performance attachment store owns files. The existing AI gateway owns provider configuration. Native notifications route generic submission tasks to the assigned manager, feedback invitations to the rater, and approval/release/plan updates to the employee. They contain no bands, rater identities or evidence text and inherit native notification entitlement and email consent. Rewards owns classification review, monetary calculations, approvals and posting.

## Assessment rules and transitions

- A cycle policy is editable only in draft, then immutable. Opening the native cycle snapshots the native grade, leadership framework and matching technical profile. Catalogue profiles can explicitly map native employments when multiple roles share a grade; otherwise exactly one company/grade default must match. HR reviews source defaults and imports the actual catalogue before opening; the package is not evidence of live tenant configuration.
- Fourteen independent windows use Malaysia offsets. Mid-year development review uses the current year; year-end plans use the next year. Goal progress and evidence remain usable throughout the year, including from historical assessment links.
- KPI definitions are employee draft → whole-scorecard proposal → manager approval or return. Weights total exactly 100%. Each line has an ordered approval chain of the assigned line manager and/or current native matrix managers. Each step consumes the preceding confirmed value; later steps cannot act early. Employee results submit once, line moderation locks each result, and the manager confirms the overall band. Changes to actuals or calculated bands require reasons.
- Mechanism A uses the highest met threshold, with a minimum rating of one. Mechanism B applies the inclusive zero gate and the source base/excellence formulas, including excess multipliers and less-is-better arithmetic. One company uses one mechanism; explicit company B bands select B. The source's less-is-better excellence example remains UNKNOWN pending an actual approved example; the implementation preserves source arithmetic rather than inventing policy.
- Technical self answers are retained. Manager overrides require reasons and are separately confirmed. Current statements weigh 1 and future statements 1.5.
- Leadership has seven principles and grade-tier statements. Numeric subjects need the configured valid-response minimum (source default four; target panel five). Non-numeric subjects use one line-manager response and cannot serve as raters. Panels use distinct people and live native relationships. Unsubmitted reviewers can decline or be replaced; submitted answers remain immutable. Employee assessment views never return rater identities, relationships, counts or individual responses. Invitation events do not use subject-readable audit scope, preventing employees from counting panel invitations through their audit access. Privileged native system-audit access remains governed by the existing audit policy.
- Potential normalizes each component before blending. Defaults use 40% leadership and 60% reviewed technical for source grades 12–23/H; an absent reviewed technical profile falls back to leadership, rather than zero. Grade normalization and valid-response requirements are explicit. Potential cutoffs and framework statements are configurable. The package's max-35 framework is not silently treated as the later unverified max-17.5 catalogue.
- Optional extreme-rater correction defaults off. It classifies the same rater's submitted answers across the cycle, adjusts that rater's own score, clamps it to the available maximum, then averages. It does not adjust another person's answer or overwrite submitted feedback.
- Calibration has explicit native reviewer grants and cohorts. Performance and potential have separate windows and locks. An unchanged assessment can pass through a locked tier without creating an override. HOD closes for an axis after BU/BG locks it; BU need not wait for HOD; BG waits for BU; Group `after` waits for BG, `replace` bypasses BG, and `blend` is advisory. Precedence is final → Group → BG → BU → HOD → manager. Group supports individual locks. PBT and potential reference curves use source boundaries and configurable tolerance; strict distribution overrides require reasons. A reviewer cannot decide their own assessment or retrieve their own entry through the calibration service. Individual Group locks do not require unrelated cohort members to have completed their assessments; strict distribution checks require an override reason if the visible distribution is incomplete.
- The source's 15-cell person talent classification is authoritative. It differs from the nine-box presentation (notably High potential / UA performance). PIP, promotion and special reward are separately confirmed decisions, never inferred from a category.
- Development plans move draft → shared → closed, with definitions locked after sharing, career-conversation completion required for closure and employee acknowledgement. Progress updates retain audit history. The 70:20:10 structure is a development prompt, not a quota invented by the integration.
- Evidence has source kinds and a 1,200-character limit, draft/shared/retracted states, objective/skill/principle links, and corrections as new entries. Shared text is immutable. Attachments use native storage and access rules. Endorsements and disputes append attributed, immutable responses from the employee or assigned manager; they never automatically adjust a rating.

## Frozen results, authorization and releases

Finalization stores the resolved bands, distinct source tiers, talent category, explicit nominations, normalized scores, policy digest, anonymous principle summary and a provenance snapshot of scoring inputs and calibration decisions. The digest identifies that frozen assessment. Legacy numeric `overall_rating` remains null: it is not a second final-rating authority.

Inputs, submitted feedback and frozen results are protected against mutation. Results release independently for performance, potential, talent and anonymous 360 summary, with explicit revocation and audit. The employee's security-definer projection returns only released components, never hidden calibration or raw source scores. Reports consume the native frozen labels and result reference instead of squeezing OneHR bands into the generic rating scale.

Services recheck module entitlement, live user state, native employment relationships and grants. Matrix managers receive only their assigned KPI lines. Calibration projections expose only the assigned cohort. Security-definer helpers have fixed search paths, explicit EXECUTE grants and tenant/actor checks. Cross-parent identity references are validated by triggers. Revisions reject stale forms; locks serialize decisions and finalization. Generic review, calibration, release, feedback and compensation writers refuse OneHR cycles, preventing a second workflow from changing their decisions.

## Rewards boundary

Rewards reads a narrow immutable projection under its own fresh GR/admin authorization, exact company roster and reward year, excluding the actor's own person. It selects the latest assessment period and prefers year-end where periods coincide. A Performance grant is not conferred on a Rewards reviewer.

A Group Rewards reviewer explicitly imports finalized results into an annual draft unit. Import invalidates classification verification and earlier approvals. `Super Star`, `Star`, `Solid Core`, and `PIP/Improvement` map to SSTAR, STAR, SCORE and IMPRO. Only an explicitly confirmed PIP flag maps to PIP; existing case evidence and human case review remain intact. Promotion and special-reward nominations are shown as evidence for human recommendations, not automatic awards. The source result ID/digest actually imported is retained independently of later compensation/roster refreshes. Existing Rewards calculations, BU → BG → GR → CTRO → EC approvals and atomic native posting remain responsible for pay.

## AI

The gateway receives only authorized notes and shared evidence, with native PII redaction. The model proposes a closed list of evidence indices; deterministic adjudication resolves only existing passages, rejects unknown/duplicate references or oversized drafts, and silently discards failure. Fresh access and evidence are rechecked after the provider call. The native proposal ledger records the adjudication and input digest without storing evidence text. Displayed suggestions are editable and have no action tools or assessment/pay writers.

## Verification and operational consequences

Source parity fixtures include 156 scoring cases and all 15 person talent combinations, with source provenance. Integration tests exercise real database RLS, stale writes, releases, frozen records, plans, evidence, calibration and explicit Rewards import. The full release requires TypeScript, the complete chunked gate, Next build, shadow migration, rendered UI checks and proof of arrival on the target installation. A draft policy must be reviewed against the organization's actual catalogue and live business rules before opening a real cycle.

The source's obsolete Rewards/succession routes are not revived: source Rewards was removed, while the native Rewards module already owns those decisions. Six locale catalogues contain the new keys with English fallback; this does not claim six completed translations. SMTP, Graph and Azure credentials are not transplanted; native infrastructure owns those concerns. No second Flask runtime or separate employee directory is deployed.

Opening company, grade and 360 statement snapshots remain immutable across native company transfers; calibration validates the review snapshot rather than the employee’s later placement. Rewards still resolves the employee’s current roster and company.
