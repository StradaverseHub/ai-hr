# ADR-0163 — Information-only employment corrections

- Date: 2026-10-30
- Status: implementation candidate for approved feedback 8550b282; not release acceptance.

The five corrected facts remain owned by employment (company, group/join dates, grade) and assignment (employment type). A dedicated command validates the resulting record, checks fresh Workforce maintain access and HR administration of source/destination companies, locks the employment and uses optimistic preview fingerprints. It does not invoke operational movement, entitlement, payroll or document writers.

Assignment changes start on the business day of correction; prior versions and intentional movements remain intact. A company correction is permitted only when retained organisation dimensions are usable by the destination; otherwise the operational transfer workflow is required. Country changes are operational changes. Original hire events remain immutable. Each correction appends an employment.information.corrected event with full preimage, postimage, display values, reason, actor and method. The original values are retained even when a correction is later corrected again.

Before the first change, metadata read by existing persisted payroll outputs is preserved in an append-only snapshot per payslip. The snapshot is the verified pre-correction rendering baseline, not a reconstruction of unknown original documents. It never replaces a payroll transaction. Payroll detail, review and register readers use this snapshot for the retained document profile; statutory dated readers use the correction preimage for periods preceding the correction. Legacy payslips with intervening master changes and no independently reconciled original snapshot refuse correction; the current master must never be stamped as an original issued value. Missing or ambiguous current assignments, gaps in entity history, inconsistent lifecycle/organisation records or inaccessible payroll evidence refuse the correction. Retained document artifacts are never regenerated. A bounded security-definer document projection authorizes the actual paying company (or the released self-service owner), without widening current employee or Workforce RLS. It reads monetary amounts from the canonical payslip as exact decimal strings; only nonmonetary document fields are retained. Register rows use the same financial derivation after merging retained documents. Statutory report readers supplement only RLS-hidden historical rows through a fixed, principal-checked paying-company/period projection. Current visible rows remain authoritative. The projection exposes only the identity, dated service, statutory declaration and assignment fields those financial reports already use; all other employment/profile fields stay absent. Payslip and declaration amounts remain canonical, and the existing report arithmetic, line routing and PDF owners are unchanged. Annual report scope is the authorized company/year, without the interactive payslip list’s row limit. The employer switcher’s current flag still comes only from the actual current employment, never the historical projection. The existing signatory owner permits a retained paying-company document while retaining its effective-source/year and self-service checks. The SQL employment-status derivation has one pure database owner shared with normal SQL readers and tested against the TypeScript derivation. Independently verified legacy reconciliation uses scripts/reconcile-information-snapshots.ts, dry-run by default, with atomic permission/binding checks and immutable evidence references; see docs/INFORMATION-CORRECTION-RECONCILIATION.md. Current employee reports show corrected master information; finalized payroll outputs retain their baseline. Future calculations use corrected master information and dated assignment facts. No historical recalculation is scheduled. Correction reviews and writes join the existing leave dependency lock. The year-open, earned-accrual and entitlement-reprojection owners refuse historical processing dates before an information correction in the selected cohort, before writing any ledger entries. A current/future dated run remains available; a prior-period repair requires independent review rather than silently reinterpreting corrected master data.

Excel imports use the same command. The original source and server-built preview are immutable shared import attempts of kind information_correction. The browser confirms an attempt/hash, never authoritative changes. Blank cells mean unchanged. All rows are checked first. Each employee has one transaction containing both mutation and import outcome, serialized by the attempt lock; committed items are reused on retry. Invalid rows are retained as errors. Final confirmation counts include failed and unchanged rows. There is no destructive revert; a further reasoned correction restores a value.

Historical report readers, scheduled leave consumers, RLS visibility after company correction, populated upgrades, document before/after and native concurrency checks are required acceptance evidence. The journal allocation and installation remain separate from source implementation.
