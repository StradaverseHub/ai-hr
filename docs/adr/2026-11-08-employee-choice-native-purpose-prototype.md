# Native employee-choice purpose prototype

Status: development prototype prepared; unmeasured and not adopted. No migration is allocated. Production remains held.

## Decision and evidence

Keep the production employee reader unchanged while testing one fixed native, security-invoker read purpose. The controlled JIT experiment (run 42397540021) showed a real planning/compilation cost in the earlier, unadopted unified reader: default initial/deep/department+unit whole ports were approximately 1130/1297/1099 ms, versus 275/447/247 ms with JIT off. Those results do not qualify a new native function or the current production reader. The new control is the exact reader from root `f1515376df082438ca025fb65d01a8a3330a8796`, not that older prototype. Its raw bytes and the import-rebased frozen copy are pinned independently in the installer and request.

A fixed PL/pgSQL `STABLE SECURITY INVOKER` function scopes `jit=off` through the PostgreSQL function setting. There is no `SET LOCAL jit` around a borrowed application transaction, no arbitrary SQL argument, privileged execution, new table permission, or cross-request cache. Function-scope restoration protects subsequent sibling queries and errors automatically; actual borrowed-transaction tests verify this boundary. Numbered migration and real application adoption require separate review after measurement.

## One native population and two closed ports

Nineteen typed parameters bind the captured human principal, server population, browser filters, conservative search candidate mode, independent selected ID and bounded page. The function rechecks actual `ai_hr_app` LOGIN/current identity, RR/READ ONLY, native RLS for all six relations, absence of an agent principal, current user/person/role/grant/login authority, and label administration. The outer adapter also retains canonical principal admission and the current role-based label rule. Native arrays, grants, finite calendar dates, parameter modes and numeric bounds are checked independently; app validation is not its security boundary.

Employment, authorized Person, unsuperseded NULL-ended Assignment and Company identities are projected once. Current Employment company remains authoritative even when Assignment belongs to the previous employer. Future valid_from is deliberately not a new eligibility filter. Ended employees, closed/superseded history, missing current Assignment, denied label rows and native scope rules remain governed by the current model. MATERIALIZED relations do not by themselves correct native RLS cardinality estimates; a bad nested-loop choice remains a real rejection until dense and sparse actual plans prove the work bound. Represented facets use the complete authorized server population, independently of browser search/status/organization filters. Selection is independently admitted inside that same server population; it never authorizes a command.

The `page` port emits tagged count, represented company/department/unit metadata, independent selected identity and page/search candidates. The `ids` port uses the same population/matching owner but emits only complete candidate ID/name/code facts; it never applies the page limit. Public pages retain 200, internal All retains 2000, and complete IDs may exceed 2000. An empty company array retains legacy RLS-only semantics; an explicit empty employment array means nobody. Safe offsets retain the full JavaScript range. Native dates match `isCalendarDate`'s actual years 0001–9999; no new arbitrary query-length limit is introduced.

Exact ECMAScript trim/lower/includes, total and offset remain in TypeScript. SQL admits conservative candidates, never substitutes locale-dependent SQL lower for Unicode matching, and never binds raw NUL/non-ASCII search text. Search and complete-ID transport use FETCH 512. No unbounded 50k JSON value is transferred. A PL/pgSQL RETURN QUERY does materialize a server tuplestore and may spill; the prototype must measure that cost rather than assuming streaming execution inside PostgreSQL.

## Disposable owner boundary

The installer requires both canonical worker URLs, their exact actual database, loopback, the real postgres owner, the exact disposable worker database, a private marker and the immediate validated Assignment exclusion constraint. It refuses any existing function with the prototype name. It installs unnumbered SQL in one transaction and verifies exact owner, invoker/stability/settings/signature and owner+app-only EXECUTE ACLs. Other app functions, all policies, table grants and membership edges are snapshotted unchanged. Removal requires exact installed pg_proc identity and function definition; unknown/drifted objects are preserved and refused. No installed staging or production database is targeted.

## Measurement and real native plan proof

The sole controlled selector retains the 50k fictional fixture, all 14 complete ports per implementation, unchanged 300-second case/20-second statement/300-ms lock budgets, actual current authority/history/revocation cases, and a separate below-1000-ms outcome. All retained names contain Unicode so conservative candidate transfer and exact JS work are exercised. It also checks a three-ID server population on the retained 50k fixture, outside the timed port claims.

Two phases have deliberately different, recorded app PIDs. Timing variants share one exclusive max-one backend, native app LOGIN/RRRO/RLS, JIT defaults, settings and resources; logging is absent. Plan variants share a second backend started only after the postgres owner temporarily configures auto_explain on that exact disposable database. Both variants execute the same ordered matrix/repeats within each phase, covering repeated calls and PL/pgSQL custom/generic plan transitions without forcing plan_cache_mode. Each timing covers fresh transaction/principal work, SQL transport, cursor and receiver work, and restoration proof. Resource and planner/statistics observations remain outside the timer.

Plan logging enables actual nested execution, rows/loops, buffers and settings, with per-node timing and parameter values disabled. It grants no application logging capability and changes no server/global/role settings. The exact database configuration is compared and restored; unknown drift refuses cleanup. The instrumented backend is closed first. These durations never stand in for latency measurements.

Bounded actual container logs (64 MiB, 100000 headers, fixed actual PID) must contain every unique begin/end phase: 34 phases, 17 per variant (16 retained samples plus one supplementary sparse call). Each native phase requires exactly one logged body with actual PL/pgSQL RETURN QUERY context, the exact fixed installed statement fingerprint, and one real outer Function Scan. Both actual row counts must equal the independent fictional stream expectation, including metadata/selection and complete IDs. Outer-only, reconstructed EXPLAIN, duplicate, wrong-PID, unbound, truncated or incomplete evidence refuses. All actual native body nodes undergo the unchanged exact-cardinality work/shared-buffer rejection envelope; settings must prove scoped JIT off and no JIT execution section. Full plans and failures are persisted before failing the oracle. No loop/buffer/latency threshold is relaxed.

The exclusive diagnostic session checks actual PID/native role/tenant/user/RRRO/RLS/no advisory lock and exact COMMIT/ROLLBACK defaults. Any uncertain restoration poisons the session and all later checkouts/selection. Primary work and cleanup failures are both retained; an AggregateError is never treated as an expected SQL refusal. Setup failure and timeout stop later work and close only owned clients. Final completeness requires both variants, authority, real plans, exact instrumentation restoration and every cleanup boundary. Missing measurements stay incomplete, not PASS.
