# ADR-0166 — Custom Termination types, per-type reasons, Field Controls and movement documents

- Date: 2026-10-30
- Status: implementation candidate for approved feedback 1d58019a (Movement Settings Enhancement), Step 2; not merged, tested on a target, installed or accepted.
- Amends: decision 476f23ed ("a tenant cannot invent a type that claims to be a Termination"), for Termination only. Owner sign-off: 30 October 2026, in chat, together with the Step 2 scope.
- Builds on: [ADR-0164](0164-movement-corrections-behind-closed-payroll.md) (corrections, termination reversal, import Update/Delete), [ADR-0165](0165-tenant-termination-reason-catalogue.md) (tenant reason catalogue) and [ADR-0156](0156-single-sheet-movement-import.md) (movement workbook).
- Migration: `0721_movement_type_controls` (journal idx 684, sequence 1793330000050). Unapplied.

## Context

Step 1 gave each tenant its own termination reasons and moved event-type editing onto a configuration page with a read-only Classification card. The reporter also asked that an organisation's own event types can be Termination types, that each Termination type offers chosen reasons, that each event type controls which employment fields it changes (and which need a supporting document), and that the same rules hold on screen, on save and on import.

## Decision

1. **Custom Termination (amends 476f23ed).** `termination` joins `CONFIGURABLE_BEHAVIOUR_KINDS`. The read-side guard (`resolveMovementTypeRow`) uses the same constant, so the two are extended together. Every other lifecycle kind (confirmation, entity transfer, probation extension, blacklist, both join-date kinds, resignation) stays non-mappable. Termination is a deterministic writer: its consequences (end of employment, coded reason, notice, last working day, closed assignment and reporting lines, payroll flags) do not depend on what the type is called.
2. **Classification is derived, never stored.** Termination when the resolved behaviour is `termination`, Non-Termination otherwise. On the configuration page the radio pair is a shortcut onto the behaviour of an unused custom type and is never posted.
3. **A used type's behaviour is locked.** `saveMovementEventType` refuses a behaviour change for any code the ledger references (the same in-use read as delete). Employment History resolves a recorded code's behaviour when it is read, so re-pointing a used type would re-project its history. The check runs under the exclusive catalogue lock. Every movement write now takes the shared catalogue lock when it resolves its type (`resolveInputTypeTx`), so the check and a first use cannot interleave.
4. **Termination resolves through the catalogue everywhere.** Every branch that tested the raw code `'termination'` decides by the resolved behaviour instead: the projection of `employment.terminated` (a custom Termination row keeps its own code), the recorded-exit projection of a scheduled termination, the pending-termination and future-clash rules of `planTerminationTx`, the edit pre-fill, both correction branches of `editMovementEventTx`, the Termination writer's tags and scheduled payload (which now record the chosen code) and the Personnel page's edit pre-fill. The sweep, `correctabilityOf`, the replay planner, `movementCorrectionBaseTx` and the import already read the resolved behaviour. `setEmploymentInfo` (core/org.ts) strips an exit type's tag outside the exit-date authority for a custom code too. A custom Termination therefore runs the same writer, reversal (`reverseTerminationTx`) and correction as the built-in one.
5. **Per-type reason lists.** `movement_type_termination_reason` holds the reasons a Termination type offers. No rows means every active reason. The writer refuses a reason the type does not offer, for a new termination and for a correction that changes the reason or the type. Correcting only the dates of an older exit does not re-judge its reason. Deleting an unused reason removes its ticks. If every ticked reason is later switched off, the type offers none until the list or the reasons change.
6. **Field Controls.** `movement_type_field_rule` holds, per comparison type and field, Want to Change This, Allow to Edit, Required to Change and File Enabled (none, optional, required). Dependencies are enforced by CHECKs and by `normaliseMovementFieldRule`. A grid equal to the defaults is stored as no rows. No rows means today's behaviour. Entity Transfer's company is always included, editable and required to change. Enforcement is in the server writer: `dispatchMovementEventTx` (New Event, import Create, rehearsal) and both comparison branches of `editMovementEventTx` (manual Edit, import Update). "Changed" is the writer's own delta rule against the same baseline the write diffs. A field outside the type's grid that changes is refused, a non-editable field that changes is refused, a Required to Change field that does not change is refused. A Required document is needed when its field changes. The sweep and the replay of later movements during an older correction never consult the rules, so history recorded before a rule existed is never re-validated. A correction is a new write and does meet the type's current rules.
7. **Supporting documents.** `movement_attachment` follows `profile_change_attachment`: PDF, PNG or JPEG checked against the file's leading bytes, 5 MB each, 5 files and 10 MB per movement, bytes in a tenant-RLS row, append-only (SELECT and INSERT grants only). Documents are keyed by the movement's group id, which covers a pending movement and the legs the sweep writes for it. A correction copies the corrected movement's documents for fields that still accept documents, and they count towards Required. Only comparison types take documents.
8. **Permissions.** Viewing and editing event-type settings (including reasons and Field Controls) stays admin-only (`super_admin`, `hr_admin`) in the service, behind `requireAdmin()` pages and admin-only write policies. Reading the controls inside a movement write needs no admin role. Movement documents are read only through `movementAttachments` and `readMovementAttachment`, which require an admin with workforce view of the employee and a movement that the employee's projected history shows. The table's read policy adds the compensation read predicate for documents filed against Basic Salary, Currency, Pay Mode or Payment Term, and its insert policy the compensation write predicate. Every refusal of a download is a 404.
9. **Audit.** `movement-type-reasons.saved` and `movement-type-field-rules.saved` (on the `movement-event-type` aggregate, with before and after values) are appended only when a control actually changes. They are written in the same transaction as `movement-event-type.saved`.
10. **Import.** The import cannot carry files. A row that changes a field whose document is Required is refused with `movement_document_required`, and other Field Controls refusals become `movement_field_*` row codes naming the field. The workbook's active-type list carries each type's controls, which are a Termination type's effectively offered reasons with their names and a comparison type's Field Controls. The signed catalogue fingerprint therefore covers reasons and rules, and the Reference sheet and the reason look-up use the tenant's reason catalogue.

## Consequences

- Turnover and termination reports are unchanged: they read `employment.termination_type`, which a custom Termination writes through the same writer.
- Workbooks downloaded before this change no longer match the catalogue fingerprint for a tenant with an active Termination type, and are refused as stale. A new download is needed.
- An Edit that only adds a document to an otherwise unchanged movement is still refused as "no change". Adding evidence to an old movement without correcting it is not built.
- In the current role model every principal with workforce view of an employee also has pay access to that employee. The pay-field predicate on documents is therefore defence in depth that today's roles cannot exercise separately.
- New translations in all six locales need translation review.
