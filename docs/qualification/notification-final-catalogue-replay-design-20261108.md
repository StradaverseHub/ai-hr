## Pre-migration seam and the real worker template

scripts/migrate-with-focused-prerequisites.ts initially migrates the development
DB, while test/global-setup.ts separately migrates a schema-only template and
clones workers. We must not confuse those databases or claim that a development
DB catalogue is the worker's native inventory.

PostgreSQL16 GetNewObjectId uses a cluster-wide counter protected by OidGenLock
([primary source](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/access/transam/varsup.c#L480-L546)).
Consequently, fixed allocation on the SAME authenticated job cluster before the
first candidate migration can change later template object allocation. This is
an inference from the allocator implementation, not a promised numeric OID shift.
The actual paired captures must prove canonical OIDs differ; otherwise the
perturbation is inconclusive. No new globalSetup provisioning/admission branch,
forged worker pool ID or replay marker table is needed.

Two thin selectors, created/registered by root, will each admit a real complete
controlled-database-v1 job and call one exported compiled case registration:

- test/notification-final-catalogue-baseline.test.ts: canonical allocation.
- test/notification-final-catalogue-oid-shift.test.ts: fixed unrelated allocation
  BEFORE canonical SQL on the actual shared job cluster, then the SAME SQL.

Each independently scheduled unit has its own fresh physical job PostgreSQL
cluster, one worker, exact current candidate/controller/complete-plan binding,
first attempt, standard runner/resource profile and original native prerequisites.
They are development commissioning observations, never a full-release receipt.
No focused admission, forged full hints, alternate database URL or caller-selected
variation is accepted. Variation derives ONLY from the exact sole registered
file in the independently reconstructed actual controller plan.
