## Compared courses

A. A literal UnsetEnvironment for SGX_AESM_ADDR is the smallest source change and preserves stockExecStart plus all existing process/observer guards. It fixes only this known host field and requires another source correction for the next unrelated global default. It is safe as a narrow repair but does not satisfy the requested sustainable boundary by itself.

B. A reusable fixed environment-projecting exec constructor can remove all unqualified incoming names immediately before os.execve, keeping secrets only in the environment vector. It can use the same mainPID via exec, no extra unit/listener and no value telemetry. However the current mandatory next_profile.unit_configuration check requires the systemd ExecStart executable/argv to be the stockNode invocation; next_fixture_poststart also requires that exact declaration. A Python→Node constructor needs a new explicitly qualified declaration lineage, source-sealed constructor, fixed finalNode argv proof, supported release/node metadata handling and native actual-exec controls. Simply adding a helper while accepting a different executable would bypass existing proof. A generic path/context interface or duplicate launcher policy would enlarge scope. This is a legitimate later design if required; it is not a trivial one-line filter and cannot be smuggled into the present guard.

C. RECOMMENDED bounded refinement of A: a private declarative manager-input projection constructor. Observe the actual manager's typed Environment KEYS, compute every key outside the existingAPP/FLEET/SYSTEMD sets, and construct UnsetEnvironment for those names in the two owned stockNext units. This handles arbitrary future GLOBAL manager defaults without naming SGX in the projection algorithm. It uses systemd's final environment assembly, keeps the exact stockNode ExecStart, leaves guard620 and the existing observer whole, and requires no new launcher/credential file/profile fields. It is smaller than B and reuses the current installation/declaration owner.

The recommendation is deliberately scoped to this pinned systemd255.4 fixed service declaration. A late-changing manager key or a newly unsupported per-process builtin must still fail unchanged guard620. No periodic snapshot can guarantee an unchanging root manager. Future systemd versions and new PAM/socket/credential/directory service features require their own source qualification rather than silent acceptance. This is fail-closed, not a claim to transparently support every future executor feature.
