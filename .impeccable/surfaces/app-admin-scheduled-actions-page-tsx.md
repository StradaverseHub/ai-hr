# Scheduled actions — runner controls

Mode: Operate. Extension of the existing Scheduled Actions route, not a new visual world.

Purpose: an installation operator sees every runner's actual activation separately from its last execution outcome, understands its data effects and result location, and changes an approved schedule. Customer group administrators retain read-only monitoring and aggregate history.

First viewport: existing page header, a factual environment/connection strip, and the first runner rows. Each row puts the purpose and two explicit status labels before timing and result navigation. No invented health, metrics, or activation inferred from code presence. Missing controller means unavailable, never off. Failed saves instruct refresh because an operation may have partially applied.

Interaction: expand Configure runner, choose activation and optionally schedule, acknowledge the visible effect warning, then save. Preserve monthly/annual business dates. Keep current-run execution separate from the future schedule. No run-now action in this change. Production replacement-holiday reconciliation and backups remain held in the controller itself.

World: inherit DESIGN.md, shared Card, Badge, Button and Input. Flat divided rows, existing semantic colors with text labels, restrained focus, responsive stacked timing fields. No images or decorative motion. Existing run-history panels follow the inventory.

Quality bar: keyboard-accessible disclosures and labels, pending/error/live-result states, truthful unavailable and external states, no customer write controls, explicit Malaysia time. Verify desktop and phone, light and dark, with a synthetic controller fixture clearly separated from live verification. English operational vocabulary is the initial locale fallback pending translation review; no translated acceptance claim.
