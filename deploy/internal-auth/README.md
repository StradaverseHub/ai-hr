# Embedded HR authentication

The owner cancelled Keycloak activation on 2026-10-15. Use `AUTH_PROVIDER=internal`; no identity-service process, OIDC discovery, `/identity` proxy or cloud identity dependency is required. ADR-0116 owns the design. The old Keycloak activation helper on the current server is disabled. Its installed service and legacy tables are retained for reviewed cleanup rather than destructively removed.

## Installation and owner enrollment

Deploy the tested additive release and migration `0543_embedded_authentication` first, preserving current access. Do not seed or replace HR data. Authentication needs a canonical HTTPS `AUTH_PUBLIC_ORIGIN` and a fresh 32-byte hex `AUTH_SESSION_KEY`; keep the key outside the database and source/build archives. Back up the app environment privately before changing it. Losing that key makes stored credentials, authenticator secrets and SMTP credentials unreadable. Do not rotate it by simply changing the variable; a controlled decrypt/re-encrypt migration and session revocation is required. Restore needs the matching key and database backup together.

Organization codes are operator-owned login namespaces, not grants. A cloud deployment may host many codes; an on-prem installation may configure `AUTH_DEFAULT_ORGANIZATION` for convenience. Every code binds exactly one existing tenant. A code cannot be reassigned to another tenant, and existing namespaces cannot silently change. Phones still select an operator-signed company setup file to choose the trusted API installation; the login organization code then selects its credential namespace.

Run `bootstrap.sh` as the installation administrator from `/opt/ai-hr`. It prepares missing public origin/key settings, asks privately for the owner username, email, organization and temporary password, and invokes the audited owner CLI using the migration connection. The CLI selects an exact existing active group administrator by internal UUID and preserves all HR IDs/grants. An explicit installation-owner option enrolls installation SMTP authority; ordinary customer administrators must not receive it. Existing exact enrollment is idempotent and never changes a live password or MFA. The current reviewed owner HR UUID is `22222222-2222-2222-2222-222222222222`; that is specific to this installation, not a customer seed.

Only after verifying TLS and owner enrollment, select `AUTH_PROVIDER=internal`, set `ALLOW_DEMO_SESSION=false`, validate `internalConfig()` and restart the already-built app. Every account's initial login must change its temporary password and prove a newly enrolled authenticator. Owner interaction is required; do not collect their password, OTP, QR or recovery codes in chat or logs. The app refuses every HR session until that completes. Keep an explicit operator rollback to the backed-up demo configuration available; there is no automatic demo fallback.

## SMTP and recovery

After verified owner sign-in, use Admin → System Settings → Email delivery. Internal mode owns an encrypted SMTP draft/active configuration in the HR database and uses the app's Nodemailer transport; it does not read Keycloak's SMTP settings. Draft testing sends only to the enrolled operator's verified address, and activation requires explicit receipt confirmation within 30 minutes. SMTP credentials are never reflected in the UI, logs, audit or mobile app. This implementation supports implicit TLS with certificate/hostname verification; a STARTTLS-only relay requires explicit additional support.

Password recovery uses organization plus username, always returns a generic known/unknown-account response, and queues a 30-minute single-use link in an encrypted outbox. The raw token travels in a URL fragment; the web page removes it from history and submits it only in a JSON POST. GETs and link scanners never consume it. Existing MFA or a recovery code remains necessary. Changing the password revokes all sessions/challenges and does not remove MFA. Backup codes are one-time and displayed only at authenticator enrollment; keep them privately. No support impersonation or email-only MFA bypass exists.

Run the app-user `scripts/internal-auth-maintenance.ts` worker every minute to retry encrypted authentication mail. The request path also wakes delivery after recovery requests. Expired record pruning must run separately as the migration owner using `select app.internal_auth_prune()`; never put owner database credentials into the web service or run application-writable source as root in a scheduled job. Add these commands through the installation's reviewed scheduler, preserving unrelated jobs. A request-triggered send is not proof of a working recurring retry schedule.
